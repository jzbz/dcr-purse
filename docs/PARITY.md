# Parity ledger

Maps every dcrwallet package, and every linked dependency the port has to supply, to its planned dcr-purse crate, its specification and its status. Parity pin: dcrwallet master `54b85b33` (2.2.0-pre). dcroxide revision: `f4b3d2e`, moved from `5c6742f` on 2026-11-19 over dcroxide's `5ce3046` (Rust 1.100.0) and `f4b3d2e` (redb 5.0.0 in `dcroxide-database`), neither touching a crate dcr-purse links ([SKEW.md](SKEW.md), ADR-0006 rule 2). The project name `dcr-purse` and the crate prefix `purse-` are final (project owner, 2026-11-18; ADR-0005).

Status values: **not started**, **in progress**, **ported** (implemented, upstream tests ported), **pinned** (differential coverage against the Go oracle in CI), **n/a** (deliberately not ported, with the reason). `sntrup4591761`, `purse-txauthor` and `purse-store` move to pinned only after fuzz soaks of each, and `purse-txauthor` after a fuzz target of its own, which it does not have yet (project owner, 2026-11-19). *The target, `fuzz/fuzz_targets/txauthor.rs`, exists since 2026-11-20; none of the three has been soaked.*

The first libraries are implemented: `errors`, `pgpwordlist` and `walletseed`, dcrd's `hdkeychain`, and the read path of bbolt (a test utility only, not shipped in the wallet: ADR-0013). `purse-snacl`, `purse-dcrutil`, `purse-mixsolver`, `sntrup4591761` and `purse-store` are in progress. `purse-txrules` (`wallet/txsizes`, `wallet/txrules`) and `purse-txauthor` (`wallet/txauthor`) are ported, with their differentials and frozen vectors run so far on x86-64 Linux only. Everything else is not started. The rows marked "pinned" below have their upstream tests ported and a differential against the Go oracle that CI runs on Linux (x86-64 and arm64), macOS and Windows, with frozen Go-generated vectors beside it. What holds each parity clause of the Phase 1 exit, test by test, is recorded in [PHASE1-EXIT.md](PHASE1-EXIT.md).

## Deliberate divergences from dcrwallet

Recorded as they are decided. So far, by decision of the project owner:

- **The database.** dcr-purse keeps its own database format and does not open, write or produce dcrwallet's `wallet.db` (2026-11-14; engine `redb` 5, 2026-11-18, ADR-0003). It does not import one either: the one-way import of a schema-26 database decided on 2026-11-14 was dropped on 2026-11-18, and migration is by seed restore only (ADR-0013). No dcrwallet database version is read or tracked, and none of dcrwallet's 25 upgrade steps is ported. A restore gives the same keys and addresses, including the leading-zero derivation and the legacy and SLIP0044 coin types (brief §3 W1; spec 02 §5.1, §5.10), and finds the wallet's funds and history through account and address discovery and a rescan, as dcrwallet's restore does (spec 09 §4.13, §4.16). What that costs, as the owner was told and accepted:
  - A user who no longer has the seed cannot migrate.
  - Everything not derived from the seed is not recovered, and must be re-entered by hand if wanted: imported private keys, scripts and extended public keys; voting accounts; account names (accounts are rediscovered by number); per-account passphrases; mixed-account configuration; agenda, tspend and treasury-key voting preferences; VSP ticket records and fee-payment state; unmined and unpublished transactions; outpoint locks. (Discovery names each account it finds `account-<n>`, `wallet/discovery.go:786`; spec 09 §4.16.1 step 3.4.)
  - Coins on addresses beyond the address-discovery gap limit are not found unless the gap limit is raised. dcrwallet's discovery bisects over segments of `gaplimit` addresses per branch (default 20) and of `accountgaplimit` accounts (default 10), assuming use is contiguous at that granularity, so used addresses or accounts past an unused segment can be missed (spec 09 §4.16.4 to §4.16.6; spec 21 §4.1.1, options 24 and 29). In SPV mode the account search probes a fixed sequence of segments instead of bisecting, and can miss used accounts even within a gap of the last one found: with accounts 0 to 31 used, it finds accounts up to 29 (spec 09 §4.16.2, Q-11).
  - Restore needs account and address discovery plus a rescan, which takes time, where an import would have been a copy (spec 09 §4.13, §4.16).
  - Further points found while recording the decision, not put to the owner, are ADR-0013 Open points 7 and 8; point 7 (watching-only wallets move by being created again from the account extended public key) was decided as proposed on 2026-11-19, point 8 remains Proposed.
  - "Drop-in" covers the network, both RPC APIs, the command line and configuration, and the same seed giving the same keys, addresses, balances and history; it no longer includes importing a `wallet.db`.
  - Under Decrediton, which expects to open an existing wallet, the wallet is created or restored through Decrediton's own flow.

Divergences in the crates implemented so far. Each has a test, and none changes a value dcrwallet produces on input it accepts:

- **`purse-errors`.** Where Go's `errors.Is` panics inside `match` on a nil level ([QK-0628](QUIRKS.md)), the level does not match and the walk goes on, so `is` can be true where Go gives no answer. A typed-nil `*Error`, a kind outside the 21, and an `E()` call with no arguments cannot be written. A foreign (non-wallet) error is an opaque leaf: matching does not follow its `source()`, where Go follows a foreign `Unwrap` ([QK-0728](QUIRKS.md)). Stacks are Rust backtraces, not Go's `debug.Stack` bytes.
- **`purse-seed`.** Inputs are `&str`, so text that is not valid UTF-8 cannot reach the decoders. A failing random source is an error; Go's cannot fail. The seed words dcrwallet echoes in decode errors are echoed here too, because clients see that text. The daemon's log will not carry them, where dcrwallet's does: decided 2026-11-18, to be implemented with the gRPC server ([QK-0729](QUIRKS.md)).
- **`purse-hdkeychain`.** Keys own their bytes: `neuter` and `zero` do not alias as Go's do ([QK-0713](QUIRKS.md)), and `serialized_priv_key` lends a read-only slice instead of the key's own storage ([QK-0714](QUIRKS.md)); every dcrwallet call site that zeroes a key was traced and none depends on the aliasing. `priv_key_bytes` on the empty private form, which only a zero child sum produces, is an error where Go's `PrivKeyFromBytes` would give the zero scalar.
- **`purse-snacl`.** Argon2id's lanes are filled in parallel on a pool made for the derivation, one thread per lane and at most one per CPU, where Go starts a goroutine per lane; the key is Go's. If the operating system refuses a lane thread, the calling thread fills every lane alone and returns the same key, where Go's runtime ends the process when it is refused a thread (ADR-0008, addendum on Argon2id's lanes; `tests/refused_threads.rs`).
- **`purse-boltread`.** A read-only bbolt reader, a test utility only since 2026-11-18 (ADR-0013): it does not ship in the wallet and is no longer the foundation of an importer. `purse-snacl`'s tests open real dcrwallet fixture databases with it, and the logical-export conformance checks (`purse-export-check`) cross-read Go-written databases with it; both are in progress. The owner may later remove it (ADR-0013 Open point 2). Its divergences from bbolt are unchanged: one non-blocking shared lock instead of bbolt's blocking wait, and on Windows a share-mode open instead of bbolt's byte-range lock. Page sizes below 1024 or not a power of two are refused; bbolt reads them, dcrwallet never writes them. When both meta pages are invalid the fallback page size is 4096, not the host's, which changes only which error is reported. On files bbolt did not write: a tree deeper than 64 levels, a page reached twice in a walk, keys out of order under a cursor, and a logical page over a configurable 256 MiB are errors; wherever Go panics or reads outside a page, an error is returned ([QK-0730](QUIRKS.md)).
- **`sntrup4591761`.** No divergence in any output: key generation, encapsulation and decapsulation give Go's bytes on every input, malformed keys and ciphertexts included, and draw Go's bytes from the random source in Go's order (one 3044-byte draw per polynomial, where Go makes 761 four-byte reads of the same stream). The random source's error is returned unchanged; with Go's `bytes.Reader` that is `EOF` or `unexpected EOF` as Go's `io.ReadFull` gives them, which the tests model. Decapsulation returns `(SharedKey, Choice)` where Go returns `(*SharedKey, int)`. Only the sort Go 1.26 and later produce on a 64-bit target is implemented: an unsigned sort of the random words, which is what dcrwallet's `go 1.26.0` requirement builds; a Go 1.26+ build for a 32-bit target, or any build with Go 1.25 or earlier, derives other keys and ciphertexts from the same seed (spec 12 open question Q40, decided by the project owner on 2026-11-19: the unsigned sort only, with no switch for other builds). Ciphertext aliases in the last three bytes are accepted as Go accepts them ([QK-0740](QUIRKS.md)). Unlike Go, private keys, shared keys and every secret intermediate are wiped. The arithmetic is not Go's but gives Go's bytes: the ring multiplications sum each coefficient as one dot product and reduce it once, which is the exact product Go's per-term reductions also give on every `int16`/`int8` input; the reciprocals are constant-time divsteps (bitsliced in R3, Montgomery products in Rq), which give the unique inverse Go's loop gives and report invertibility exactly, and leave in their output no inverse when there is none, which key generation discards as Go does (spec 12 §5.10.4). Go's procedures are kept as the test model (`src/reference.rs`) and checked against Go, inputs with no inverse included. Measured by `tests/timing.rs` on one core of an x86_64 Linux desktop with Go 1.27.4 (ADR-0014; every operation is a secret path, bounded at 1.15 times Go's time): key generation 1.40 ms against Go's 18.7 ms (0.075), encapsulation 70 µs against 2.38 ms (0.029), decapsulation 149 µs against 6.54 ms (0.023); the direct port of Go's arithmetic took 8.43 ms, 2.26 ms and 6.49 ms. A dudect-style test found no timing difference between a fixed and random streams in key generation, a fixed and random r in encapsulation, or, in decapsulation, a fixed and random ciphertexts under one key, valid and invalid ciphertexts, and a fixed and random private keys (|t| ≤ 3.1 in three runs against dudect's 4.5); each decapsulation class reads its inputs from a pool of the same size, since one hot fixed ciphertext against a pool of cold ones measured as a difference of its own. The timing comparison and the dudect-style test are ignored tests run by hand; a CI timing gate is deferred (project owner, 2026-11-19). Still to come (project owner, 2026-11-19): a replay of the published NIST known-answer decapsulations for sntrup4591761.
- **`purse-txrules`.** Sizes and script lengths are Go `int`, `i64` here, with Go's wrapping arithmetic; every input gives Go's answer except these. `is_dust_amount` answers `true` (dust) for a script size of -184, where Go's estimated cost is 0 and it divides by zero; no dcrwallet call site passes a negative size ([QK-0741](QUIRKS.md)). `stake_pool_ticket_fee` returns an error of kind `Invalid` where Go's big-integer division panics because the ticket price cancels the vote subsidy; the price comes from the network backend (ADR-0012 Rule 2(c); [QK-0742](QUIRKS.md)). It computes the vote subsidy from the parameters each call is given, where Go keeps one process-wide subsidy cache built from its first call's parameters; dcrwallet passes the same parameters on every call ([QK-0269](QUIRKS.md)). dcr-purse's callers are to hold a `StakePoolFees`, which keeps the cache for one `Params` (project owner, 2026-11-19). A NaN or out-of-range VSP percentage converts as amd64 converts it on every target (ADR-0012 Rule 9(a); [QK-0743](QUIRKS.md)). A Go `MsgTx.SerType` other than the three serialization types and a `stdscript.ScriptType` outside the 21 defined values cannot be represented; only Go code produces either (ADR-0012 Rule 4).
- **`purse-txauthor`.** Amounts and sizes wrap as Go's `int64` and `int` do, and the loop asks the input source for Go's targets in Go's order. Where Go panics or dies it returns an error instead (ADR-0012 Rule 2): `randomize_output_position_with` and `randomize_change_position_with`, of kind `Invalid`, for no outputs or an index outside them, which `spendoutputs` reaches without a change output ([QK-0263](QUIRKS.md), [QK-0492](QUIRKS.md)); `add_all_input_scripts`, kind-less, for a pay-to-pubkey previous or redeem script whose key does not parse ([QK-0745](QUIRKS.md)), and for a merge into a nested pay-to-script-hash signature script, exactly where Go recurses until the stack overflows: the new signature script, built with the script builder's limits as Go builds it, is nonempty, parses and ends in a push of a plain pay-to-script-hash script, and the existing one is nonempty and parses ([QK-0746](QUIRKS.md)). A secp256k1 key from a secrets source is read as Go's `PrivKeyFromBytes` reads it (any length, at most 32 bytes taken, reduced modulo N) and signs as in Go, which dcroxide's signer alone would refuse; an ECDSA key that reduces to zero is refused with `invalid privkey`, where Go signs with it for the point at infinity (an error in P2PK and P2PKH scripts, a skipped key in multisig; ADR-0012 Rule 7; [QK-0682](QUIRKS.md); accepted by the project owner, 2026-11-19). dcrwallet's own secrets source passes only 32-byte reduced keys, so from the wallet only a zero imported key reaches this. A change source declaring a script size of -184 gets no change output where Go's dust test divides by zero ([QK-0741](QUIRKS.md)). The bounded draw is Go's `Int32N`, so the same stream gives Go's positions; production draws from `dcroxide-crypto`'s process-wide generator, taking its lock per 64-bit draw where Go holds it for the whole `Int32N`. The loop moves the caller's outputs and the source's inputs into the transaction where Go aliases the slices (spec 10 quirk 18). A nil input detail, change source or secrets source, and a signature type outside dcrec's three, cannot be represented (ADR-0012 Rule 4). Where a retry would ask the input source again for the target it was just asked for, `new_unsigned_transaction` returns its insufficient-balance error, `txauthor.NewUnsignedTransaction: insufficient balance` (ADR-0012 Rule 2(a); project owner, 2026-11-19), without making the repeated call; every call before it is Go's. The owner's ruling named the overflow of the output total plus the fee as the condition; the repeated target is used instead because Go ends normally after some overflowing targets, so a check on the overflow would diverge where Go answers, and because the same loop is reached without the target overflowing ([QK-0753](QUIRKS.md)). The condition as implemented awaits the owner's confirmation. A repeat needs a wrapped sum: an output total within the fee of `math.MaxInt64`, whether the source answers with no inputs or with inputs that cover the total but whose own fee wraps the retry ([QK-0744](QUIRKS.md)), or a source amount exceeding a wrapped output total by more than `math.MaxInt64`, as for a total of `math.MinInt64` ([QK-0753](QUIRKS.md)). Go asks for the repeated target again and ends only if the source then fails or answers differently; the wallet's sources answer it the same way, so there Go never ends. Only that stall, of period 1, is refused, and it is the only one a source whose answer settles can cause (any cumulative source, the wallet's `udb` source and its all-outputs wrapper among them); a source whose answers make the targets cycle with a period of 2 or more loops forever here as in Go (`longer_cycles_keep_go_s_loop`). The differential and frozen vectors compare the refused cases with Go's answers cut by the test source's call limit (`go_endless_loop`), and `div_qk0744_endless_loop_is_an_error` shows Go never answering.
- **`purse-store`** (in progress: brief Phase 2's exit tests pass; the wallet-wide rows of ADR-0001's `[wallet]`, `[masterkeys]`, `[cryptokeys]`, `[cointypes]` and `[chain]` sections have their tables, and the records for multisig, voting accounts, VSP, agenda and treasury policies and spec 05's aux buckets are not written). Its file is its own redb format (above). A second open of a store that is open, from another process or another handle in the same one, fails at once with kind `Other` and redb's text ("Database already open"); bbolt, and so dcrwallet, polls every 50 ms without end and without a log line (spec 01 §5.2). Engine errors carry the kind of the nearest bbolt condition (spec 01 §8.1) and redb's own text (ADR-0011 ET-006). A store newer than the build is refused with dcrwallet's kind and text, `invalid operation: database has been upgraded to an unknown newer version` (`wallet/udb/open.go:36-38`), the two versions being available to the caller but not in the text; the refusal changes no row, though redb has taken the file for writing by then and its open and close rewrite the header and commit slots, so the file's bytes change. Each migration step is its own transaction, where dcrwallet's `Upgrade` runs every pending step in one (`wallet/udb/upgrades.go:1717-1726`): a crash leaves either at a version boundary, but dcr-purse's can stop between two steps of one upgrade (ADR-0003 Decision item 6). `WriteTx::len` (and with it the `unspent` count, which is the table's length, not a stored counter) counts the transaction's own puts and deletes, where bbolt's `KeyN` in a write transaction does not (spec 04 §5.1 item 6, QK-0003). dcrwallet calls `KeyN` of `unspent` in read transactions and in one read-write transaction, `txToMultisig`'s (wallet/createtx.go:553, through `findEligibleOutputsAmount` at :601 and :1911), which writes nothing to `unspent` before the count, so the two agree there; `purse-udb` must keep that order or reproduce bbolt's committed-only count for that call (the divergence accepted by the project owner, 2026-11-19, with that Phase 3 obligation). The cursors are bbolt v1.3.12's in every answer a read transaction gives, and in a write transaction as long as the cursor's table has not been written since the cursor's last `First`, `Last` or `Seek`, or since a `Prev` that ran off the start when no leaf of the table had been emptied (bbolt's `Prev` calls its `first`, a fresh descent, every time it runs off the start), writes to other tables never mattering, except around leaves emptied earlier in the transaction (the four defects below); a cursor `Delete` after `Next` ran off the end removes the last entry and after `Prev` ran off the start the first, as in bbolt (QK-0019), unless the leaves after that last entry were emptied in the transaction, where bbolt's removes nothing (QK-0749). Writes between a write cursor's moves follow one rule where bbolt's answer depends on its page layout (QK-0004, bolt#620): every move reads the table as it then is, `next` returning the first key above the one the cursor stands on and `prev` the last below it, so a deleted entry is never returned and none is skipped or repeated; bbolt skips one after a cursor `Delete` on a leaf already written in the transaction. After `next` ran off the end the cursor still stands on the entry it ran off from, so an entry put above it since is the next `next`'s answer; bbolt's agrees on a leaf already written in the transaction and returns nil on one that was not, its cursor then reading the leaf's committed copy (`div_next_after_next_off_the_end_misses_a_put_on_a_committed_leaf`). Every `prev` that finds nothing repositions the cursor on the table's first entry as the table then is, or on nothing if it is empty, as bbolt's `Prev` does, a second `prev` off the start included. Four bbolt defects under mutation are not reproduced (accepted by the project owner, 2026-11-19): its `Prev` into a leaf emptied earlier in the transaction returns nil (QK-0747), where the store returns the key below; after its `Next` ran off the end over leaves emptied in the transaction its cursor stands on the empty last leaf, so `Delete` removes nothing and `Prev` returns the entry it ran off from again (QK-0749), where the store deletes that entry and steps below it; its `Last` on a bucket of several leaves emptied in the transaction never returns (QK-0750), where the store's returns nothing; and its cursor `Delete` panics with an index out of range when never positioned (spec 01 §5.7) or after `Last` on a bucket emptied in the transaction and a later `Put` (QK-0748), where the store removes nothing. QK-0747, QK-0749 and QK-0750 need a bucket of several leaves, so which buckets reach them depends on bbolt's page size, which a dcrwallet database takes from the host that created it (4096 bytes on x86-64 Linux and Windows, 16384 on Apple silicon): at 16 KiB a bucket needs about four times as many entries; QK-0748 does not depend on it. The conformance test sets bbolt's page size instead of taking the host's: 4096 bytes for every script, and 16 and 64 KiB as well for these four, the named cases and a random corpus, which agree under the same rule at every size. dcrwallet reaches none of these: it never calls a cursor's `Delete`, collects keys before it changes the bucket it walks, and where it does not (upgrade 17, QK-0119) overwrites only the entry it stands on, where bbolt and the store agree. bbolt's limits on a `Put` are kept with its kind and text (an empty key, `invalid operation: key required`; a key over 32,768 bytes, `invalid operation: key too large`; a value over 2^31 - 2 bytes, `invalid operation: value too large`, which the chain operations check on every filter they are given before they write anything, so that the refusal leaves the transaction usable where dcrwallet's caller abandons its bbolt transaction). During initial sync, header-and-filter batches and the rescan marker commit without durability except every 50th commit, counted over every sync running on the handle on however many threads (each commit decides its durability and updates the count under one lock, since redb's writer lock ends inside the commit), and the end of the sync (ADR-0003 Decision item 9, ADR-0014 Open point 2), where dcrwallet's bbolt syncs every commit: after a power loss the store reopens at the last durable commit or later, never between two commits, and the sync fetches the lost batches again; nothing else is committed without durability, and a header batch cannot connect or detach a block row with wallet transactions or the stake-invalidation flag. Main-chain block headers and committed filters are keyed by height beside the block records, and those of blocks not in the main chain by hash in tables of their own, where dcrwallet keys every header and filter by hash in its `h` and `cf` buckets (ADR-0003, ADR-0014 Open point 6); a reorganisation moves a block's header and filter between the two in the transaction that detaches it, nothing is pruned, and a lookup by hash finds a main-chain or a detached header or filter as dcrwallet's does, at the cost of a second read (the hash-to-height index) for a main-chain block. The chain operations refuse a main chain that is not contiguous from height 0, and a header that does not state the height it is connected at or does not name the block below. A main-chain block delivered again with its own header is refused with dcrwallet's kind and text (`Exist`, `block already recorded in main chain`), the check made as `ExtendMainChain` makes it (`wallet/udb/txmined.go:204-226`): at the height the header states, before the height the caller gives and the parent are looked at, for each block of a call in order, and in a reorganisation for a block at or below the fork point, as after dcrwallet's `Rollback`; so a port of dcrwallet's notification path, which ignores `Exist` and goes on to the block's transactions (`wallet/chainntfns.go:45-49`), sees the same refusal. A header stating height 0 above the genesis block, or a height of 2^31 or more on any chain (dcrwallet's `int32(header.Height)` is negative there, `wallet/udb/txmined.go:204-207`), is refused before that with dcrwallet's `Invalid` text `block 0 cannot be added`, so the operations never put a block above height 2^31 - 1; for the first block of an empty chain, which dcrwallet never passes to `ExtendMainChain`, refusing such a header is the store's choice. Two refusals have no counterpart in dcrwallet: the caller gives the height, which must be the one above the tip (dcrwallet takes it from the header), and a hash already in the main chain offered with a header stating another height is refused with kind `Invalid`, where `ExtendMainChain` would record the block a second time at the new height and overwrite its header in the `h` bucket (read from the source, not run); neither arises for a hash that is its header's. The operations do not hash headers, so that a block's hash is its header's is the caller's to ensure. A write transaction whose commit fails at a storage operation may still be kept: redb applies it fully or not at all, and which is known only after a reopen. The store's error says so (`Error::commit_outcome_unknown`), so that `purse-udb` re-reads rather than retries; bbolt, under dcrwallet, has the same uncertainty and no way to say it: its commit writes the meta page and returns the error of the `fdatasync` that follows, the page possibly already written (bbolt@v1.3.12 tx.go:542-566; read from the source, not run).
