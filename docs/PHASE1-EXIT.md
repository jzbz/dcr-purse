## 1. Account xpubs and first addresses, 10⁶ seeds and every leading-zero seed

> for at least 10⁶ random seeds plus every seed whose path contains a leading-zero key in a targeted search, account xpubs and the first addresses of both branches equal the Go oracle's

**Held by** `crates/purse-hdkeychain/tests/wallet_diff.rs` *(until 2026-11-22; since then by `crates/purse-udb/tests/wallet_diff.rs`, through `purse-udb`'s address manager: the dated note of 2026-11-22 at the end of this section)*, against the oracle command `wallet` of `tools/oracle/cmd/hdkeychain` (`wallet.go`). For each seed, Go calls dcrwallet's own `udb.HDKeysFromSeed` (what wallet creation and restore call) for the legacy and SLIP0044 coin type keys and account 0 of each; derives account 1 as `udb.Manager.NewAccount` does (reached through `Wallet.NextAccount`), from the coin type key re-parsed from its string; serializes each account's extended public key as the wallet stores it; and makes the first address of the external and internal branch from that key re-parsed, through `deriveBranches`, `deriveChildAddress` and `compat.HD2Address` (an internal package, copied verbatim into `compat.go`; `compat_test.go` fails if the copy drifts from the pinned module). The Rust side (`tests/common/wallet.rs`) composes `purse-hdkeychain` and dcroxide-txscript's `stdaddr` (the address encoding dcr-purse uses) in the same steps. Per seed and coin type, one line carries the neutered coin type key, and one line per account carries the account xpub and both addresses: four account lines per seed.

Account 0 comes from the coin type key as derived, which `hdkeychain` stores stripped of leading zero bytes when it has them; account 1 comes from the re-parsed key, padded back to 32 bytes. The two routes give different accounts exactly when the coin type key was stored stripped (spec 02, the stored-stripped quirk), so both are compared.

*2026-11-22: the differential runs the code that ships.* **Held by** `crates/purse-udb/tests/wallet_diff.rs`, against the same oracle command `wallet`, whose Go side and lines are unchanged. The tests moved out of `purse-hdkeychain` because `purse-udb` depends on `purse-hdkeychain`: calling `purse-udb` from `purse-hdkeychain`'s tests would need a dev-dependency cycle, which Cargo builds but which turns `purse-hdkeychain`'s `chaincfg` feature on in every one of its own test builds (feature unification through `purse-udb`'s dependency) and makes the key crate's tests depend on the wallet crate built on it; no crate of the workspace has such a cycle. The test names, the labels their inputs are drawn from (so the same seeds), the default sizes and the frozen set are unchanged; the frozen file is now `crates/purse-udb/tests/data/wallet_lines.txt`, its body and body hash unchanged (only its header's provenance lines name the new regenerator), and `tools/pinmove`'s table lists it under `purse-udb`. For each seed the Rust side builds two address managers, each on its own `purse-store`, as two wallets made from the seed hold them: one keeps the legacy coin type, as a restored wallet does, and one is moved to SLIP0044 with `Manager::upgrade_to_slip0044_coin_type`, as a new wallet is. Each is created from the seed with `Manager::create` (which calls `addrmgr::hd_keys_from_seed` and stores the coin type keys and account 0), opened, unlocked and given account 1 with `Manager::new_account`; its lines are read through public operations only: the coin type from `Manager::coin_type` (so the coin type is compared too), the `C|` key from `Manager::coin_type_priv_key` neutered, and each account's xpub from `Manager::account_extended_pub_key`. The first addresses take four operations, because the address a listing returns is not the derivation that recorded it, and dcrwallet hands addresses out from a fourth. While the manager is unlocked, `Manager::sync_account_to_addr_index` records child 0 of both branches: it derives each publicly from the account xpub parsed from the store and stores only the path (account, branch, index) under the HASH160 of that derivation, the hash index by which a wallet recognises its addresses. `Manager::for_each_account_address` builds each listed address by deriving its path again, privately while the manager is unlocked and publicly from the account xpub once it is locked (`chainAddressRowToManaged`); the test lists the rows once unlocked, then locks the manager with `Manager::lock` and lists them again, compares the locked, public listing with Go (derived as Go's `deriveBranches` and `deriveChildAddress` derive it), and requires the unlocked, private listing to equal it. Finally `Manager::address` looks each compared address up by its HASH160 and must find the row of that same path (account, branch, child 0), which is what checks the derivation `sync_account_to_addr_index` keyed its rows by, since no listing reads it back. Last, `Manager::account_branch_extended_pub_key` (Go's `AccountBranchExtendedPubKey`, from which dcrwallet's address buffers derive account 0's addresses right after the coin type upgrade, `wallet/cointype.go`, and during discovery, `wallet/discovery.go`) must give, for each branch, a key that serializes as the compared account xpub's child of that branch and whose child 0's P2PKH address is the compared address. A seed `HDKeysFromSeed` refuses fails in `Manager::create`, whose error is the seed's `E|` line. The composition in `tests/common/wallet.rs` is removed with the old tests: every step it took (master, hardened children from stripped and padded keys, neutering, serialization, re-parsing the account xpub, public children of it, `stdaddr`'s P2PKH encoding) is taken by the managers on the same seeds and reaches the compared lines, so it compared nothing the new path does not; the new path also compares the private children and the hash index, which the composition did not have.

A first version of these tests, reviewed before it was committed, listed the addresses with the manager unlocked and did not look them up. Two defects passed it, each shown by a mutation in a copy of the source: `sync_account_to_addr_index` deriving each branch's child from the other branch (so each branch's hash index held the other branch's address), because the listed string came from the private re-derivation and not from the derivation that keyed the row; and a public child derivation giving a wrong child 0 below a branch key, because no compared address went through public child derivation (the composition's tests caught it, as do `purse-hdkeychain`'s own vectors, but not at this clause's scale). With the lock and the lookup, the first fails `frozen_wallet_lines`, `random_seeds_match_go`, `leading_zero_seeds_match_go`, `seed_lengths_match_go` and `dcrwallet_scrypt_costs_give_the_same_lines` on the lookup, and the second fails the same five on the private and public listings' disagreement and, with that check disabled, on the comparison with Go. A third mutation, a wrong public key for a private child 0 below a branch key, fails the same five on the listings' disagreement. A second review found that no compared value went through `account_branch_extended_pub_key`, the operation dcrwallet hands account 0's addresses out from after the coin type upgrade and in discovery: with it mutated to derive the other branch's key, `wallet_diff` passed, and only `purse-udb`'s other tests failed (`frozen.rs`, `oracle.rs`, `properties.rs` and `upstream.rs`: operation scripts, properties and upstream examples on a few dozen seeds). The branch-key check above was added; with the same mutation the same five tests fail on the branch key's serialization and, with that assertion disabled, on its child 0's address. The unmutated tests pass.

Three test-only parameters keep a wallet per seed affordable; none reaches derivation. The managers get each network's chain parameters with `simnet` set, which `purse-udb` reads only to pick simnet's scrypt cost (N = 2, r = 1, p = 1) instead of dcrwallet's N = 2^18, r = 8 (four 256 MiB derivations per manager: two at creation, one at open, one at unlock); the name, extended-key versions, coin types and address prefixes are the network's own, and `cheap_parameters_change_only_the_scrypt_cost` checks that `simnet` is the only field changed. The stores are in memory (redb's `InMemoryBackend` under `purse-store`), so no commit waits for a sync. Salts, crypto keys and nonces come from a fixed SplitMix64 stream instead of the operating system. ## 3. Key blobs in both directions

> secretbox/Argon2 blobs written by Go open in Rust and the reverse

**Go to Rust.** `crates/purse-snacl/tests/oracle.rs` `differential_against_go`: 1,178 requests over 17 commands, each answered by Go and replayed by Rust, including every box and blob Go sealed (scrypt master-key parameters, XSalsa20-Poly1305 boxes under a crypto key and under a master key, Argon2id parameters, XChaCha20-Poly1305 account blobs), each opened with the right key, a wrong key, one flipped bit and every truncation; Rust reproduces each Go-sealed value byte for byte from the same nonce. `frozen_vectors_against_go` and `frozen.rs` hold the same as frozen vectors. `crates/purse-snacl/tests/fixtures.rs` opens the keys sealed in every upstream fixture database (`wallet/udb/testdata`, v1 to v24) and `generated_db.rs` and `generated_database_against_go` every sealed value of a whole database Go's `udb` wrote, at dcrwallet's real costs (Argon2id at 256 MiB included).

**Rust to Go.** `crates/purse-snacl/tests/oracle.rs` `rust_written_blobs_open_in_go` (new): values this crate writes with its own randomness, through the plain constructors a wallet uses, are opened by the Go oracle: 6 scrypt master-key parameter sets (three small costs, snacl's defaults N = 16384, r = 8, p = 1, and the two costs dcrwallet itself writes, `udb.scryptOptionsForNet` at the pin: N = 2^18, r = 8, p = 1 on mainnet, testnet3 and regnet, N = 2, r = 1, p = 1 on simnet), from which Go derives the same key and refuses a wrong passphrase; 18 boxes sealed under those master keys (each master key sealing a fresh crypto key, as a wallet's do, an empty and a random plaintext); 24 boxes sealed under the crypto keys; Argon2id parameters from `Argon2idParams::new` (operating-system salt, this machine's thread count) read back by Go; and 9 account blobs under keys derived at three small Argon2id costs, opened by Go through `account-unseal` (which re-derives the key from the parameters and passphrase) and `unseal`. Go must also refuse each kind of value once tampered with: every box and account blob with one bit flipped (account blobs through both `unseal` and `account-unseal`); each scrypt parameter set with a bit flipped in its salt or digest, truncated by a byte, and with a wrong passphrase; the Argon2id parameters with a bit flipped in the salt (`account-unseal` with the right passphrase must then fail) and truncated by a byte (`argon2-unmarshal`). Bits of the cost fields (scrypt's N, r, p; Argon2id's time, memory, threads) are not flipped: a flipped high bit asks Go for terabytes of memory. The test asserts these counts. `dcrwallet_scrypt_costs_are_the_ones_go_wrote` (same file, no oracle needed) holds the two dcrwallet costs the test uses to databases Go wrote: both master key parameter sets of each upstream fixture (testnet3) carry N = 2^18, r = 8, p = 1, and those of the generated simnet database N = 2, r = 1, p = 1.

**Not covered:** the Rust-to-Go direction derives Argon2id keys at small memory costs only; dcrwallet's 256 MiB Argon2id cost is used from Go to Rust (the generated database) but not from Rust to Go, to keep the test suite fast. (scrypt at dcrwallet's real costs is covered in both directions.) dcr-purse writes no database, so no whole Rust-written database is opened by Go.

*2026-11-21, at Phase 1's closing: dcr-purse writes databases. `purse-store` (since 2026-11-19) creates them, on redb rather than dcrwallet's bbolt, and `purse-udb`'s address manager (since 2026-11-20) seals its keys into them with `purse-snacl`. ## 4. Error rendering

> error rendering equals Go's for a generated corpus of nested errors

**Held by** `crates/purse-errors/tests/oracle.rs` `differential_against_go`: 24 fixed programs and 600 random ones (2 to 9 nodes each, every node an `E` with up to five arguments, a literal `*Error`, a bare kind, `errors.New`, a `%w` wrap of up to three earlier values or a join, so values nest through earlier ones), each under the daemon separator `":: "` and the library's `":\n\t"`: 1,248 evaluations, comparing for every value the rendered text, the chain after `E`'s promote and collapse rules, `Is` against every kind and every other value, `As`, `Unwrap` and the stack count. Go panics in about 400 `Is` queries per run (the deliberate divergence QK-0628); those are not compared. `frozen_vectors` replays 168 frozen programs (the fixed ones under both separators and 120 random ones) and the kind table without Go. `crates/purse-errors/tests/deep.rs` builds, renders and drops chains a million levels deep on a small stack.

## Speed (ADR-0014's Phase 1 row)

> no slower than Go on public derivation, address, script, HMAC, hash160, base58; secret paths (master, hardened and private child with public key) ≤1.15× [Go's time]; [at least] 1.5 times faster on 20,000 addresses

**Measured by** `crates/purse-bench` against `tools/oracle/cmd/bench` (dcrwallet's own packages at the pin), the two alternating in one session, 5 processes per side; the workloads, inputs and their mapping to the clauses are in `crates/purse-bench/src/lib.rs`. Both sides' outputs (keys, addresses, scripts, digests) are cross-checked in every process (the solver workloads cross-check the instance, and each side checks its own solver's roots against it before timing), and `crates/purse-bench/tests/smoke.rs` (`smoke_session_agrees_with_go`) holds the two sides to the same 27 outputs in every test run (21 before the cycling workloads of 2026-11-21, which add the count and two digests of each of their two input sets).

**Result,** 2026-11-19, the ledger's first entry (a shared desktop, measured processes pinned to four cores; to be confirmed on a dedicated machine): met for public derivation (Rust's time 0.55 of Go's), address (0.56), script (0.55), HMAC-SHA512 (0.86), hash160 (0.84), base58check encode (0.95), and the 20,000-address workload (1.80 times as fast). **Undecided** for base58check decode: the entry measured 0.98, but nine later sessions on the same machine and commits gave 0.98 to 1.02 (missed in four of them, by the driver's verdict), so decode is at parity with Go and the margin the entry showed is noise (the ledger's dated note under the first entry). About half of Rust's decode time is dcroxide-crypto's portable BLAKE-256 against Go's AVX assembly, a cause in dcroxide; the clause is decided by the dedicated-machine run or given real margin by a dcroxide change. **Not met** for the secret paths: master key 1.59, hardened child 1.58, private child 1.57 times Go's time, against at most 1.15. Profiled: about 90% of a hardened derivation is k256's generic constant-time multiplication of the generator, which dcroxide-dcrec builds without precomputed tables (ADR-0014 O1); the fix belongs to dcroxide and is being made there. The clause is met once the dcroxide pin includes it and a ledger entry shows it. *Decided by the project owner on 2026-11-19 (ADR-0014, addendum of that date, items 1 and 2): the speed clause stays open until the dcroxide pin includes dcroxide `5ace7a2` and the row is measured again, and base58check decode is settled by a measurement on a dedicated machine. Measured again on 2026-11-20: the next paragraph.*

**Measured again,** 2026-11-20, the ledger's entry "The secret paths at dcroxide `2074168`" (three sessions of the first entry's command on the same shared desktop, 15 processes per side, measured processes pinned to the same four cores; ADR-0014, addendum of 2026-11-20). With the dcroxide pin at `2074168`, which includes dcroxide `5ace7a2` (k256's basepoint table for the generator), **the secret paths meet the row**: master key 0.86, hardened child 0.84, private child 0.85 times Go's time (0.75 to 0.87 across the three sessions), against at most 1.15. The clauses met before are met again: public derivation 0.54, address 0.56, script 0.55, HMAC-SHA512 0.83, hash160 0.81, base58check encode 0.94, the 20,000-address workload 1.80 times as fast. **base58check decode is still undecided**, at parity with Go: 1.01 pooled, 1.02, 1.01 and 0.99 by session (missed in two of the three by the driver's verdict). **The speed clause is therefore not closed.** The one workload short of the row is base58check decode, Rust/Go 1.01 against at most 1.00; it is settled by the dedicated-machine run, which is also still to confirm the rest of the row.

*2026-11-21: the dcroxide pin moved to `48f5b5e`, whose `dcroxide-base58` converts in limbs of several digits instead of one digit or byte a step, with decred/base58's outputs and errors (`docs/SKEW.md`, 2026-11-21 section). `purse-bench`'s two base58check rows call `dcroxide-base58` directly, so they now time the new conversion. The row has no measurement of record at this pin; the speed clause stays open on base58check decode until a ledger entry measures it.*

*2026-11-21, later: the base58 workloads behind every base58check figure above repeated one input on both sides (the decode workload one address, the encode workload 256 hashes differing in their last byte; the bench ledger's notes of this date give the code), so the decode ratios of 0.98 to 1.02 are ratios for one address decoded again and again, not evidence of parity on varied input. `crypto.base58check_encode` and `crypto.base58check_decode` now cycle through 16,384 different mainnet addresses, built alike on both sides and cross-checked, and `crypto.base58check_decode_one` keeps the old decode workload. No session has been timed with them; the decode clause is decided by the first ledger entry that does.*

*2026-11-21, the project owner (ADR-0014, addendum of that date, item 2): a run on the shared desktop with nothing else running on it counts as the dedicated-machine run, or the run may be made on another machine; no timed run of record is started until the owner says when and where. None has been made. The speed clause stays open on base58check decode, Phase 1 is not closed, and no timing figure is recorded here.*

**Measured on the dedicated machine,** 2026-11-21, the ledger's entry "Phase 1's row on the dedicated machine at dcroxide `48f5b5e`": three sessions of the ledger's command at dcr-purse `1f7316e`, 15 processes per side, measured processes pinned to the same four cores, on the shared desktop with no other job running on it (the entry lists what a `top` snapshot before each session showed), which counts as the dedicated-machine run (ADR-0014, addendum of 2026-11-21, item 2), made when the project owner said that day that the machine was quiet and told the run of record to be made on it. One-minute load average 0.63 at the start and 0.76 to 1.14 during the sessions, the measured processes themselves. All 27 cross-checked outputs were equal in all 30 processes. **base58check decode meets the row**: Rust's time 0.78 of Go's, pooled and in each of the three sessions (Go 351 ns, Rust 274 ns per decode, cycling through 16,384 different mainnet addresses; Rust's slowest process faster than Go's fastest). Every other clause is met again: master key 0.86, hardened child 0.85, private child 0.85 times Go's time, against at most 1.15; public derivation 0.55, address 0.55, script 0.56, HMAC-SHA512 0.87, hash160 0.85, base58check encode 0.45, against at most 1.00; and the 20,000-address workload 1.80 times as fast, against at least 1.5. Each session's own ratios give the same verdicts.

Phase 1 is closed on 2026-11-21, on the project owner's instruction of 2026-11-20 to finish Phase 1 and the owner's authorisation of this run as the run of record.
