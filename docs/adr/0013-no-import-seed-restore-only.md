# ADR-0013 — No database import: migration by seed restore only

- **Status:** Accepted (project owner, 2026-11-18). In the owner's words:
  "scrap import, seed restore only", chosen to simplify wherever possible.
  It reverses part of the owner's decision of 2026-11-14 (own database
  format plus a one-way, lossless, non-destructive import of a dcrwallet
  `wallet.db` at one schema version): the own format stands, the import is
  dropped. It supersedes [ADR-0007](0007-importable-dcrwallet-databases.md)
  in full, so decision D4 of the brief falls away, and voids the import
  front end of [ADR-0005](0005-name-data-directory-and-import-front-end.md),
  so D1 shrinks to what ADR-0005 keeps. What the owner accepted is Decision
  items 1 to 10. Everything under Open points, and the statements Context
  marks "found after the decision", are Proposed: not put to the owner, not
  decided by this record.
- **Open points all decided, 2026-11-22 (project owner):** points 1 to 5
  and 7 on 2026-11-19; point 9 and point 6's Phase 8 bullet on 2026-11-22
  ("Accept all eight"); and later the same day point 6's other bullets
  and point 8, each as proposed. Shown them with the recommendation to
  accept them as proposed, together with ADR-0019's FB13 and a cut-off
  rule for questions arising in working out ADR-0019, the owner answered
  "Accept all three"; that is the whole of the answer. Point 8 confirms
  the three statements Context marks "found after the decision" other
  than watching-only wallets (point 7): the first two join Decision item
  4's list, by a dated note there, and its copies; the third is owed to
  the user documentation of point 4, which is not yet written. No point of

- **Date:** 2026-11-18

## Context

Citations of the brief in this section are to the brief as of commit
`d190bda`, before this decision; the living brief has since been revised to
match it.

**What was decided on 2026-11-14.** dcr-purse keeps its own database format
(engine `redb`, now `redb` 5, accepted 2026-11-18 and recorded in ADR-0003)
and never opens or writes dcrwallet's `wallet.db` in place; a dcrwallet
database at schema version 26 is imported once, one way, without modifying
it and without the private passphrase (brief §1, §3 W2, §9 D4;
`docs/PARITY.md`, "Deliberate divergences"). On 2026-11-18 the importable
version was fixed as the pinned dcrwallet's `DBVersion`, one version only
(ADR-0007 Decision item 3), and the name, data directory and import front
end were accepted (ADR-0005; its import front end is kept there, struck or
in its Appendix A).

**Why import existed.** The brief's project statement was that a user could
"stop `dcrwallet`, import its `wallet.db` once" and keep "the same accounts,
addresses, balances, history, tickets and preferences" (brief §1). W2
listed what an import was to carry: account names and numbers, the
last-used and last-returned counters, imported keys, scripts and xpubs,
voting accounts, per-account passphrases, unmined and unpublished
transactions, agenda, tspend and treasury-key preferences, VSP ticket
records, birthday and rescan markers, stored headers and filters (brief §3
W2). None of that is derived from the seed; the import was the only route
the plan offered for it.

**What import would have cost.**

- **Decoders for every bucket at one schema version.** The importer's
  specification was the description of dcrwallet's on-disk format: specs
  [01](../specs/01-walletdb-bbolt.md), [02](../specs/02-address-manager.md),
  [03](../specs/03-txstore-formats.md) and
  [05](../specs/05-db-migrations-aux-buckets.md), about 8,000 lines
  together (`docs/specs/README.md`, the table of specs). The crate
  `purse-import` was to hold them (brief §5).
- **Phase 3 sized XL**, "Wallet database logic and the importer", with an
  exit over a version-26 import corpus generated by the Go oracle (brief
  §6, Phase 3; §11).
- **Tracking dcrwallet's `DBVersion`.** Each pin move that raises it would
  bring new decoders, a new Go-written corpus, and new refusal text
  (ADR-0007 Decision item 3; Consequences, "a pin-move checklist entry for
  `DBVersion`"). `DBVersion` is 26 at the pin (`wallet/udb/upgrades.go:213`).
  Inside version 26, files written by 2.0.x releases can hold states the
  pinned code does not write (ADR-0007 Context).
- **The import front end** of ADR-0005: the options `--import` and
  `--importfrom`, a source search over three locations, the first-start
  offer, carried configuration and TLS files with path rewriting, seven
  exit statuses, and a verification report (ADR-0005 Decision items 3 to 8,
  in its Appendix A).
- **Hostile-file parsing in the wallet process.** The importer was to run
  inside the daemon, which holds keys (ADR-0005, option "Import entry
  point", in its Appendix A); the bbolt reader is hardened against corrupt
  and hostile files for that reason (brief §6, Phase 2; ADR-0012 Rule 8).
- **Edge handling** decided or proposed in ADR-0007: header and filter
  checks (item 4), a table of unusual states (item 5), atomic build and
  verification (item 6), and a corpus of watching-only, legacy coin-type,
  migrated, crash-left and 2.0.x-written wallets (Consequences).
- **Risk R2, a lossy or wrong import**: "an account counter, an imported
  key, a ticket or a spent flag carried over wrongly, and the wallet
  reissues addresses, misses funds or misstates its balance" (brief §10).

**What seed restore already is in the plan.** Restore was always required
and is not new work: account and address discovery and the rescan are in
Phase 5, the M2 exit includes a testnet3 wallet restored from seed and
compared with Go, the M5 exit includes restored-from-seed discovery, and the
M7 exit includes restore through Decrediton (brief §6, Phases 5, 6, 10,
12). W1 already requires that the same seed and passphrases give the same
keys and addresses, including the leading-zero hardened-derivation variant
and the SLIP0044 coin-type upgrade (brief §3 W1). dcrwallet's `--create`
flow restores from an existing seed, asks for an optional birthday, and
accepts named xpub accounts (spec 21 §5.4.1, §5.4.10 to §5.4.12). A restored
wallet starts on the legacy coin type and discovery upgrades it to SLIP0044
only if nothing is found on the legacy path (spec 21 §5.4.1 step 6; spec 09
§4.16.1 steps 7 to 9; spec 02 §5.10). Discovery creates each found account
under the name `account-<n>` (`wallet/discovery.go:786`; spec 09 §4.16.1
step 3.4). Its gap limits are `gaplimit`, default 20
(`wallet/addresses.go:385`, `config.go:57`), and `accountgaplimit`, default
10 (`wallet/addresses.go:389`, `config.go:59`) (spec 21 §4.1.1, options 24
and 29).

**State of the code.** `purse-boltread`, a read-only bbolt v1.3.12 reader,
is committed, reviewed and pinned against bbolt in CI on Linux (x86-64 and
arm64), macOS and Windows (`docs/PARITY.md`). It is not an importer. Two
crates use it in their tests only, as a dev-dependency: `purse-snacl` reads
master-key parameters and sealed keys out of real dcrwallet fixture
databases (`crates/purse-snacl/Cargo.toml`, `[dev-dependencies]`;
`crates/purse-snacl/tests/common/mod.rs`), and `purse-export-check`'s
conformance tests cross-read Go-written databases
(`crates/purse-export-check/Cargo.toml`;
`crates/purse-export-check/tests/oracle.rs`). Both crates are in progress
and not yet committed. It also has a fuzz target
(`fuzz/fuzz_targets/boltread_open.rs`). No `purse-import` crate exists.

**Found after the decision; not put to the owner.** Writing this record
turned up four points the owner was not told about. They are not part of
what was accepted; Open points 7 and 8 put them to the owner. *(All four
since decided as proposed: the first by Open point 7, project owner,
2026-11-19; the other three by Open point 8, project owner, 2026-11-22.)*

- A watching-only dcrwallet wallet has no seed. dcrwallet creates one from
  an account extended public key (`--createwatchingonly`, spec 21 §5.4.2);
  the same flow in dcr-purse (W6) would recover what that key determines.
  Whether that counts as a migration route goes beyond "seed restore only".
- The last-returned address counters are not recovered as dcrwallet keeps
  them: after discovery the stored last-returned index is raised only up to
  the last-used index (spec 09 §4.16.1 step 6.3), so an address handed out
  but never paid can be handed out again.
- The birthday is not recovered unless the user gives one at the restore
  prompt (spec 21 §5.4.1 step 2.4, §5.4.11); without one, the rescan starts
  from genesis (spec 21 §9 item 17).
- Account discovery needs the coin-type private key, so it runs only when
  the wallet is unlocked at the moment the syncer is created (spec 09
  §4.16.1 step 3.2; spec 14 §4.12, gRPC driver item 6, and Q-52; spec 15
  Q22); a restore synced with the wallet locked discovers addresses only
  within the accounts it already has.

## Options considered

**Keep the import** as decided on 2026-11-14. Everything in `wallet.db`
moves, seedless users included, as a copy rather than a rescan, and
Decrediton users could be moved without a restore. Cost: all of "What
import would have cost" above, in Phase 3 and again at every pin move that
raises `DBVersion`, plus a parser of untrusted files in the process that
holds keys. Its strictest test, import then compare with Go on the
original, would also have been the project's strongest check of store
coverage.

**Defer the import past 1.0.** 1.0 ships with seed restore only, carrying
every loss listed under Decision item 4; an importer may follow. Cost now:
small, since the store must hold dcrwallet's logical content anyway (brief
§1, "The wallet database") and the logical export already describes it
(ADR-0001, in preparation). Cost later: the whole importer, against
whatever `DBVersion` dcrwallet has reached by then, and a release whose
users meet restore-only migration first.

**Migrate non-seed state over the RPC API of a running dcrwallet.** A small
helper asks a running dcrwallet for what the seed cannot recover and
replays it into dcr-purse: account names (`listaccounts`), imported private
keys (`getaddressesbyaccount` on the imported account, then `dumpprivkey`,
which needs the wallet unlocked), vote, tspend and treasury-key choices
(`getvotechoices`, `tspendpolicy`, `treasurypolicy`), replayed through
`renameaccount`, `importprivkey`, `setvotechoice`, `settspendpolicy` and
`settreasurypolicy` (`internal/rpc/jsonrpc/methods.go:101`, `:105`, `:128`,
`:133`, `:137`, `:154`, `:165-168`, `:176-177`). dcrwallet's own code reads
its database, so there is no file parsing and no `DBVersion` tracking, only
an API version (JSON-RPC 11.0.0). Cost: a client of both APIs; private keys
cross a process boundary; coverage is partial, since neither API has a
method that lists every stored redeem script (multisig scripts are
reachable per output through `getmultisigoutinfo`, spec 17 §5.3.28),
per-account passphrases are secrets no method reveals, and VSP ticket
records can be read over gRPC (`GetVSPTicketsByFeeStatus`,
`GetTrackedVSPTickets`, `rpc/api.proto:86`, `:90`) but no method found here
writes them back; and it needs a working dcrwallet installation at
migration time.

**Scrap the import.** Migration is by seed restore only. Removes every item
of "What import would have cost", the crate `purse-import`, the front end
and the parsing of untrusted files in the wallet. Cost: Decision items 3 to
8 below, each accepted by the owner.

## Decision

1. **dcr-purse does not import a dcrwallet database.** Migration is by seed
   restore only. There is no `purse-import`, no `--import` or
   `--importfrom`, no first-start offer, no verification report, no carried
   configuration or TLS files, no decoding of every bucket of dcrwallet's
   schema, no tracking of dcrwallet's `DBVersion`, and no compatibility
   surface W2 as written.

2. **What stands from 2026-11-14.** dcr-purse keeps its own database format
   and never opens or writes dcrwallet's `wallet.db` in place.

3. **Who cannot migrate.** A user who no longer has the seed cannot
   migrate.

4. **What a seed restore does not recover.** Everything not derived from the
   seed is not recovered, and must be re-entered by hand if wanted: imported
   private keys, scripts and extended public keys; voting accounts; account
   names (accounts are rediscovered by number); per-account passphrases;
   mixed-account configuration; agenda, tspend and treasury-key voting
   preferences; VSP ticket records and fee-payment state; unmined and
   unpublished transactions; outpoint locks.

   *2026-11-22 (project owner, Open point 8, decided as proposed): two
   items join this list. The last-returned address counters, as dcrwallet
   keeps them: after discovery each branch's last-returned index is raised
   only to its last-used index, so an address handed out but never paid
   can be handed out again (spec 09 §4.16.1 step 6.3). And the birthday,
   unless the user gives one at the restore prompt: without one, the
   rescan starts from genesis (spec 21 §5.4.1 step 2.4, §5.4.11, §9 item
   17).*

   Notes on that list, which add no item to it. Rediscovered accounts are
   named `account-<n>` (`wallet/discovery.go:786`). The `--create` flow
   accepts named xpub accounts at restore (spec 21 §5.4.12). The
   mixed-account configuration is the options `mixedaccount`,
   `ticketsplitaccount` and `changeaccount`, which name accounts (spec 21
   §4.1.1, options 70 to 72; §5.2 step 23), so a copied configuration
   resolves only once the accounts carry those names again. dcrwallet keeps
   outpoint locks in memory only, and they are empty after every process
   start (spec 07 §3.7), so an import would not have carried them either.

5. **Coins beyond the gap limit.** Coins on addresses beyond the
   address-discovery gap limit are not found unless the gap limit is
   raised. dcrwallet's discovery bisects over segments of `gaplimit`
   addresses per branch (default 20) and of `accountgaplimit` accounts
   (default 10), assuming use is contiguous at that granularity, so used
   addresses or accounts past an unused segment can be missed (spec 09
   §4.16.4 to §4.16.6; spec 21 §4.1.1, options 24 and 29). In SPV mode the
   account search probes a fixed sequence of segments instead of bisecting,
   and can miss used accounts even within a gap of the last one found: with
   accounts 0 to 31 used, it finds accounts up to 29 (spec 09 §4.16.2,
   Q-11).

6. **Restore takes time.** Restore needs account and address discovery
   plus a rescan, which takes time, where an import would have been a copy
   (spec 09 §4.13, §4.16).

7. **The drop-in claim no longer includes "import your `wallet.db` once".**
   The drop-in surfaces are the network, both RPC APIs, the command line
   and configuration, and the same seed giving the same keys, addresses,
   balances and history.

8. **Decrediton.** Running dcr-purse under Decrediton, which expects to open
   an existing wallet, needs the wallet created or restored through
   Decrediton's own flow (the gRPC loader service, spec 20; brief §6, M7
   exit). Installing as `dcrwallet` for Decrediton, (c) of D1, still waits
   for ADR-0005's Phase 8 addendum.

9. **Not decided.** Two possibilities were put to the owner and are
   recorded as possibilities only, not as plans: deferring an importer to a
   later release, and a small helper that asks a running dcrwallet over its
   RPC API for what the seed cannot recover (imported keys, account names,
   voting choices) and replays it into dcr-purse.

10. **What stays true.**
    - Seed restore was always required and stays (brief §6, Phases 5 and
      6), and W1 is unchanged: the same seed gives the same keys and
      addresses, including the leading-zero derivation and the SLIP0044
      and legacy coin-type handling.
    - `purse-boltread`, a read-only bbolt reader, is a test utility only: it
      does not ship in the wallet and is no longer the foundation of an
      importer. `purse-snacl`'s tests open real dcrwallet fixture databases
      with it, and the logical-export conformance checks
      (`purse-export-check`) cross-read Go-written databases with it. The
      owner may later remove it (Open point 2).
    - The Go oracle still reads dcrwallet databases with dcrwallet's own
      code.
    - The logical export (ADR-0001, in preparation) is still needed: it is
      how a Go wallet and a Rust wallet are compared when their databases
      share no format. Its strictest use, "import a Go-written database,
      then compare" (brief §7 Layer 2), is gone; comparisons reach the same
      state on both sides by running the same operations (the
      operation-script runner, ADR-0002, in preparation) or by restoring
      the same seed against the same chain.
    - `purse-snacl` keeps dcrwallet's key-sealing formats (scrypt with
      secretbox; Argon2id with XChaCha20-Poly1305), which are tested
      against Go, and nothing is gained by changing them. The reason "so
      that imported keys carry over without decryption" (brief §6, Phase 3;
      `docs/specs/README.md`) no longer applies.
    - Specs 01, 02, 03 and 05 are no longer an importer's specification.
      They remain the description of what dcrwallet persists, which the
      store's logic and the logical export must cover, and of the fixtures
      the tests read.

**Revisit** if users without seeds ask to migrate, or if Decrediton's
create and restore flow, once its launcher is read (brief §6, Phase 0),
