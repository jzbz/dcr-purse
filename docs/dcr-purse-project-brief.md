# dcr-purse — Developer Brief & Project Plan

**A full Rust re-implementation of the Decred wallet daemon (`dcrwallet`), built as a drop-in replacement, including SPV, StakeShuffle coin mixing and staking.**

Prepared for the implementing team. "Drop-in" covers everything outside the process: the network, both RPC APIs, the command line and configuration, and the same seed giving the same keys, addresses, balances and history. It does **not** cover the database file: dcr-purse stores its data in its own format (project owner, 2026-11-14) and never reads, opens, writes or imports a dcrwallet `wallet.db`; a user moves to dcr-purse by **restoring from the wallet seed** (project owner, 2026-11-18, ADR-0013, which drops the import decided on 2026-11-14; see §1 and W2). Parity target: **dcrwallet v2.2**, which upstream has not yet released, so the pin follows dcrwallet master: now **`54b85b33`** (2026-11-05, version `2.2.0-pre`, module `decred.org/dcrwallet/v5`). JSON-RPC API version **11.0.0**, gRPC API version **10.0.0**, dcrwallet database version **26** (what dcrwallet writes at the pin; dcr-purse does not read it, and the version is not tracked as an input), P2P protocol version advertised in SPV mode **11**, required dcrd JSON-RPC API **8.3.0 or later in major 8**.

The name "dcr-purse", taken from the repository directory, is final (project owner, 2026-11-18; decision D1, [ADR-0005](adr/0005-name-data-directory-and-import-front-end.md)).

This brief is the plan. The specifications it rests on are the 25 documents in [specs/](specs/README.md), about 55,000 lines written from the Go source at the pin and then checked against it twice (an accuracy pass and a completeness pass). Where this brief and a spec disagree on a fact, the spec is closer to the source; where a spec and the Go source disagree, the Go source wins and the spec has a bug.

## 1. Project statement (the short version)

dcr-purse is a from-scratch Rust implementation of the Decred wallet daemon. The goal is that a user can stop `dcrwallet`, restore the same seed into dcr-purse, start it with the same command line and the same configuration options (kept in `dcr-purse.conf` under dcr-purse's own data directory, ADR-0005), and nothing else notices: `dcrd` (or dcroxide) sees the same JSON-RPC client, SPV peers see the same protocol-11 peer, Decrediton and `dcrctl --wallet` get the same gRPC and JSON-RPC answers, a VSP sees the same fee payments, other StakeShuffle participants complete mixes with it, and — above all — the same seed yields the same keys, addresses, balances and history. Those are the drop-in surfaces: the network, both RPC APIs, the CLI and configuration, and the seed. Since 2026-11-18 the claim no longer includes "import your `wallet.db` once".

**Migration is by seed restore only** (project owner, 2026-11-18; ADR-0013), chosen to simplify wherever possible. This reverses part of the owner's decision of 2026-11-14, which was an own database format plus a one-way, lossless, non-destructive import of a dcrwallet `wallet.db` at one schema version. What stands from 2026-11-14: dcr-purse keeps its own database format and never opens or writes dcrwallet's `wallet.db` in place. What is dropped: the import, the crate `purse-import`, the import front end (`--import`, `--importfrom`, the offer at first start, the verification report, carried configuration and TLS files), the commitment to decode every bucket of dcrwallet's schema, the tracking of dcrwallet's database version, and compatibility surface W2 as it was written. The owner was told what this costs, and accepted it:

1. A user who no longer has the seed cannot migrate.
2. Everything not derived from the seed is not recovered, and must be re-entered by hand if wanted: imported private keys, scripts and extended public keys; voting accounts; account names (accounts are rediscovered by number); per-account passphrases; mixed-account configuration; agenda, tspend and treasury-key voting preferences; VSP ticket records and fee-payment state; unmined and unpublished transactions; outpoint locks.
3. Coins on addresses beyond the address-discovery gap limit are not found unless the gap limit is raised. dcrwallet's discovery bisects over segments of `gaplimit` addresses per branch (default 20) and of `accountgaplimit` accounts (default 10), assuming use is contiguous at that granularity, so used addresses or accounts past an unused segment can be missed (spec 09 §4.16.4 to §4.16.6; spec 21 §4.1.1, options 24 and 29). In SPV mode the account search probes a fixed sequence of segments instead of bisecting, and can miss used accounts even within a gap of the last one found: with accounts 0 to 31 used, it finds accounts up to 29 (spec 09 §4.16.2, Q-11).
4. Restore needs account and address discovery plus a rescan, which takes time, where an import would have been a copy (spec 09 §4.13, §4.16).
5. The drop-in claim no longer includes "import your `wallet.db` once" (above).
6. Running under Decrediton, which expects to open an existing wallet, needs the wallet created or restored through Decrediton's own flow.

Further points found while recording the decision, and not put to the owner (watching-only wallets, which have no seed; the last-returned address counters; the birthday; account discovery needing an unlocked wallet), are ADR-0013 Open points 7 and 8. Point 7 was decided as proposed (project owner, 2026-11-19): a watching-only wallet, having no seed, moves by being created again from its account extended public key. Point 8 remains Proposed.

Not decided, and recorded here only as possibilities the owner was told about, not as plans: deferring an importer to a later release; and a small helper that asks a **running** dcrwallet over its RPC API for what the seed cannot recover (imported keys, account names, voting choices) and replays it into dcr-purse.

Seed restore was always required and stays: account and address discovery and the rescan are Phases 5 and 6, and W1 already demands that the same seed give the same keys and addresses. dcr-purse never opens or writes dcrwallet's `wallet.db` (and by default uses its own data directory, ADR-0005), so a user's dcrwallet wallet stays as it was and can be started again. Going back is the same move in reverse — restore the seed into dcrwallet — with the same losses; a kept dcrwallet wallet does not know of accounts, imported keys, tickets or preferences created in dcr-purse after the switch. What the user documentation says about moving non-seed state is D14, whose reframing is accepted by the project owner, 2026-11-19 (ADR-0013 Open point 4).

Scope is the complete feature set of dcrwallet at the parity target:

- **The wallet database**: dcr-purse's own storage format, designed for the wallet's access patterns instead of inherited; the same logical content as dcrwallet's (the address manager with BIP0044 accounts, imported keys/scripts/xpubs, voting accounts, per-account passphrases and watching-only wallets; the transaction store; VSP, agenda and treasury-policy records).
- **Restore from seed** (the only migration path since 2026-11-18, replacing the import from dcrwallet planned on 2026-11-14; ADR-0013): creation from an existing seed through the `--create` prompts, gRPC and Decrediton, then account and address discovery with dcrwallet's gap limits, probe sequence and coin-type handling, and the rescan, in both sync modes, so that a restored wallet holds what dcrwallet restoring the same seed holds.
- **Key handling**: Decred's `hdkeychain` derivation including its non-BIP32 treatment of keys with leading zero bytes, PGP-word-list seeds, scrypt/secretbox and Argon2id/XChaCha20-Poly1305 key encryption, lock/unlock with timeouts.
- **Transaction construction**: coin selection, fee and dust rules, size estimation, change handling, signing for every script class the wallet spends, multisig, sweeps, treasury transactions.
- **Both sync modes**: RPC mode through a trusted dcrd over a JSON-RPC websocket, and **SPV mode** with the wallet's own P2P peer implementation, headers-first sync, version-2 committed filters with header-commitment proofs, and the wallet's own header and difficulty validation.
- **Staking**: ticket purchase (plain and mixed), voting with agenda, tspend and treasury-key preferences, the VSP client and its fee-payment state machine, and the automatic ticket buyer.
- **StakeShuffle mixing**: the full mixing **client** (the part dcroxide left out as wallet-side): pair requests, session formation, the six-stage DC-net run, blame, the coinjoin, the post-quantum key agreement, and the account mixer.
- **Both RPC servers**: JSON-RPC (103 implemented methods plus websocket) and gRPC (11 services, 88 RPCs, mutual TLS), byte-compatible in results and errors.
- **Operational compatibility**: all 81 options of `dcrwallet.conf` and the CLI, data directory layout (under dcr-purse's own name, ADR-0005), the interactive creation prompts, the pipe IPC protocol Decrediton uses to supervise the wallet, log format and rotation, TLS certificate and client-certificate handling, signals and exit codes.

Explicit non-goals: Go **library** API parity (dcrwallet's packages are imported by other Go programs; a Rust port cannot serve them); reading, opening or writing a dcrwallet `wallet.db` in any form — in place, by import (dropped 2026-11-18, ADR-0013) or by export back to that format (see W2); and the two command-line tools that do not work at the pin (`movefunds`, `sweepaccount`). The earlier non-goal "databases from before the unified layout (dcrwallet ≤ 0.8.2)" was an import refusal and is subsumed: no dcrwallet database of any version is read.

"Full test coverage" is defined in §7. The situation differs from dcroxide's in one important way: dcrd carries about 134,000 lines of tests for 168,000 lines of code, while dcrwallet carries about 11,000 for 66,000 hand-written lines, and whole subsystems (SPV, P2P, the gRPC server, the JSON-RPC method handlers, ticket purchase, voting, the VSP client, the ticket buyer, config) have **no upstream tests at all**; mixing integration has a single test of coinjoin detection. There is no test corpus to port. The oracle rig is therefore not one layer among several here; it is how almost every behaviour gets pinned.

Sizing reality check: this is smaller than dcroxide in lines and has no consensus engine, but it is not proportionally easier. Three things make it hard in its own way. First, **funds are at stake on every write**: a wallet that derives one wrong key, records one spend wrongly, or sets one account or address counter wrongly on restore loses track of money without any network noticing. Second, the surface that must match is unusually wide for the code size: two complete RPC APIs whose error strings and JSON number formatting are client-visible, plus a multi-party cryptographic protocol where any deviation gets the wallet blamed and excluded. Third, there is almost nothing upstream to test against, so the team builds its own oracle for nearly everything. Treat it as a multi-engineer-year project; the phase plan in §6 is ordered so that each milestone is a usable, verifiable thing (libraries → store and database logic → syncing wallet → JSON-RPC drop-in → staking → SPV → mixing → gRPC and Decrediton).

The per-spec effort estimates (S/M/L/XL relative to each other) are: fourteen L, seven M, one M–L (15), one S–M (22), one S (25), and one XL — spec 23 rates the oracle rig as a whole XL, "comparable to a large implementation crate". The other XL items appear when specs are grouped into phases (§6): the store and database logic as a whole (the store plus importer until 2026-11-18), the JSON-RPC server as a whole, mixing as a whole, and gRPC including its transport.

The wire protocol version is not a skew: dcrwallet and dcroxide both use `wire` v1.8.0, which defines protocol 12; dcrwallet's own `p2p` package advertises 11, and `dcroxide-wire` takes the version as a parameter.

dcroxide also supplies things the wallet needs that are not dcrd modules: a Go-compatible `encoding/json` emitter over a runtime type model (dcroxide's ADR-0007), a go-flags/INI compatibility layer (for v1.6.1; dcrwallet pins **v1.5.0**, which differs), the slog log format and a log rotator (inside `dcroxide-node`, not yet a library; the rotator ports logrotate v1.1.2 where dcrwallet pins v1.0.0, whose pruning loop and compression path differ), an in-tree TLS provider, HTTP/1.1 and websocket **server** framing, a SOCKS dialer, and the whole oracle-rig method (dcroxide's ADR-0001).

**dcr-rs cannot be linked as it stands.** Its only curve backend is the libsecp256k1 C binding, which dcroxide's `deny.toml` bans by name under the pure-Rust rule (dcroxide's ADR-0012). For every concern both projects cover, the dcroxide crate is the dcrd-parity implementation and the wallet takes that one. What dcr-rs contributes is design and vectors: its `hd` module already models the "stored stripped" key provenance that Decred's hardened derivation depends on (about one seed in 128 derives differently from plain BIP32 somewhere on the wallet path), and its test vectors come from dcrd. The wallet's `hdkeychain` should be a new crate over `dcroxide-dcrec` that takes that design, with dcrd's exact parsing and error behaviour. Note also that dcrwallet seeds are **not** BIP39: they are raw 16–64 byte seeds shown as hex or as PGP-word-list mnemonics with a one-word checksum.

**Neither project had** a bbolt reader when this was written; dcr-purse now has one, `purse-boltread`, built for the importer and kept since 2026-11-18 as a test utility only (ADR-0013; §5). `purse-hdkeychain` has since been built too ([PARITY.md](PARITY.md)). **Neither has**: a wallet store (dcroxide's `redb`-based storage per its ADR-0004 is the obvious starting point for the engine), a websocket or JSON-RPC **client**, HTTP/2, gRPC, protobuf, the mixing client, sntrup4591761, a root solver over the mixing field, a VSP API client (dcroxide's graph has `ureq` 3.5.1 for its seeder, bound to `dcroxide-tlscrypto`; whether the VSP client uses it is a Phase 0 decision), scrypt/Argon2id/secretbox wiring, or terminal prompt handling.

## 3. The compatibility contract — what "drop-in replacement" means, precisely

Every task serves one of seven surfaces. They are in priority order; a W1 failure loses money.

**W1 — Keys and funds (absolute).** The same seed and passphrases produce the same extended keys, account keys, addresses and scripts as dcrwallet, for every account type and every branch, including the leading-zero hardened-derivation variant and the SLIP0044 coin-type upgrade. Every output dcrwallet would recognise as the wallet's, dcr-purse recognises; every output dcrwallet could spend, dcr-purse can spend, with signatures that dcrd accepts. No sequence of operations or crashes may leave funds unspendable or silently unrecorded. Switching back to dcrwallet is outside this guarantee (§1). This is the surface where "close" is not a grade.

**W2 — Moving from dcrwallet: seed restore only.** dcr-purse keeps its own database (2026-11-14) and does not read, open, write or import a dcrwallet `wallet.db` (2026-11-18; ADR-0013). The surface W2 named until then — a lossless, one-way, non-destructive import of a schema-26 database — is withdrawn. A user moves by restoring the wallet seed; §1 lists what that costs. The contract on that path is accepted by the project owner, 2026-11-19 (ADR-0013 Open point 1, quoted): "Given the same seed and passphrases, the same network and chain, and the same options that steer discovery (`gaplimit`, `accountgaplimit`, `disablecointypeupgrades`; spec 21 §4.1.1, options 24, 29 and 30), a wallet restored in dcr-purse holds what dcrwallet restoring the same seed holds, in RPC mode (discovery over dcrd's exists-address index, spec 09 §4.16.4, §4.16.6) and in SPV mode (over committed filters, spec 09 §4.16.2, §4.16.5): the same accounts by number; the same last-used and last-returned child index per branch, so that the next address issued is the one dcrwallet would issue; the same active coin type, legacy or SLIP0044 (spec 09 §4.16.1 steps 7 to 9; spec 21 §9 item 17); the same birthday and rescan point; the same balances by category, mined transaction history, tickets and their commitments; and the same discovery outcome, including what dcrwallet's discovery fails to find (beyond the gap limits, and the account probe sequence of spec 09 Q-11, under its quirk decision). State the seed does not carry is absent on both sides; where dcrwallet offers an RPC to set it, re-entering it by hand is covered by W4 and W5." The specs of dcrwallet's on-disk format ([01](specs/01-walletdb-bbolt.md), [02](specs/02-address-manager.md), [03](specs/03-txstore-formats.md), [05](specs/05-db-migrations-aux-buckets.md)) are no longer an importer's specification: they describe what dcrwallet persists, which dcr-purse's store logic and the logical export must cover, and the fixture databases the tests read. What W2 does not require: bbolt compatibility of any kind in the wallet, schema-26 byte layouts in dcr-purse's own store, the upgrade chain, tracking dcrwallet's database version, or any of the byte-level quirks of dcrwallet's rows — only the behaviour those rows produce through the APIs.

**W3 — Interoperability on the network.** (Replaces "W3 — What the network sees", under which dcr-purse was to be indistinguishable from dcrwallet to its peers; the project owner put speed ahead of that on 2026-11-19, and accepted this text the same day: [ADR-0014](adr/0014-performance.md).) Transactions, tickets and votes are built as dcrwallet's are, so they relay and mine alike. In RPC mode the wallet is the same JSON-RPC client to dcrd. In SPV mode it speaks protocol 11, and every dcrd and dcroxide node accepts and serves it correctly: nothing it sends gets it banned, throttled, disconnected or deprioritised, needs a message or version they refuse, or abuses a peer. Where it can be faster than dcrwallet within those bounds, it is, and each wire-visible difference is recorded in PARITY.md. It reveals no more about which addresses, transactions or blocks are the wallet's than dcrwallet does, unless the owner decides otherwise. To a VSP it sends the same signed requests in the same order; to other mixers it is indistinguishable: any deviation in pairing data, message bytes, PRNG consumption or blame logic is detected by honest peers and gets the wallet excluded from the mix.

**W4 — JSON-RPC API 11.0.0.** All 103 methods plus the 8 dead names, HTTP POST and websocket transports, HTTP Basic and client-certificate authentication, positional-parameter parsing with Go's leniencies, results byte-compatible with Go's `encoding/json` (member order, omitted members, `null` versus `[]`, float formatting of amounts such as `1e-08`), the same error codes, and error messages that match dcrwallet's own text (see D9 for where the line is drawn on text that Go's standard library authored). Acceptance oracle: `dcrctl --wallet` and existing JSON-RPC integrations work unmodified.

**W5 — gRPC API 10.0.0.** All 11 services and 88 RPCs over HTTP/2 with mutual TLS, the same protobuf messages (tag-ordered output, presence of empty sub-messages), the same status codes and messages, the same streaming behaviour (ordering, readiness gating, what a half-close does). Acceptance oracle: Decrediton operates unmodified, including wallet creation, restore, sync in both modes, ticket purchase, mixing and voting-preference changes.

**W6 — CLI, configuration, lifecycle.** Every option with the same names, defaults, precedence and validation errors under go-flags v1.5.0 semantics; the same data directory resolution per OS and network (under dcr-purse's own name, ADR-0005); the interactive `--create` flows prompt for prompt, the existing-seed restore included; exit codes; signals; and the pipe IPC protocol (`--pipetx`, `--piperx`, `--rpclistenerevents`, `--issueclientcert`) that Decrediton relies on to learn the listener addresses and receive its client certificate.

**W7 — Operational artefacts.** `rpc.cert`/`rpc.key` and `clients.pem` handling, the log line format and rotation, subsystem tags and the `--debuglevel` grammar, and the SPV address-manager peers file.

Where dcrwallet's behaviour is a defect, the default is to reproduce it when an external observer could depend on it, and to record it in [QUIRKS.md](QUIRKS.md) with a pinning test. The deep dive recorded more than seven hundred candidate behaviours (732 entries in QUIRKS.md), each still to be confirmed by an oracle run. Three classes get a standing rule instead of case-by-case treatment (decision D10; [ADR-0012](adr/0012-standing-quirk-policy.md), accepted 2026-11-18, is the policy as decided and supersedes this summary where they differ): where Go **panics** on malformed data, dcr-purse returns an error; where Go's result order is **random** (map iteration), dcr-purse picks a deterministic order; and where reproducing a defect would **lose funds or leak secrets**, dcr-purse fixes it and records the divergence in [PARITY.md](PARITY.md). ADR-0012's Rule 8 (the `wallet.db` reader may refuse input Go accepts) now governs only the test utility `purse-boltread`, since no shipped component reads a `wallet.db` (ADR-0013).

## 4. Engineering principles

These are dcroxide's, adjusted where a wallet differs. [specs/25-reuse-dcr-rs-and-conventions.md](specs/25-reuse-dcr-rs-and-conventions.md) lists each dcroxide ADR and whether it carries over unchanged, needs a wallet decision, or does not apply.

1. **dcrwallet is the specification.** The specs in `specs/` are a map of it, not a replacement for it. When a spec is unclear, read the Go at the pin and reproduce it — including quirks — then fix the spec.
2. **Oracle-driven development, more than ever.** Every module ships with vectors generated by Go shim programs linked against dcrwallet's own packages at the pin, and, where feasible, a differential test that runs the same script of operations through Go and Rust and compares the replies and a logical export of the resulting wallet state (§7). Nothing is "done" on the strength of a hand-written expected value.
3. **No hand-rolled cryptography for standard algorithms.** scrypt, Argon2id, XSalsa20-Poly1305, XChaCha20-Poly1305, BLAKE2b, SHA-2, HMAC and curve arithmetic come from reviewed crates under dcroxide's dependency rules. The project owns only what has no maintained implementation: `hdkeychain`'s Decred variant, sntrup4591761 at its 2017 round-1 parameters (byte-compatible down to how randomness is consumed), the mixing DC-net and key agreement, and the root solver.
4. **Memory safety, and secrets treated as secrets.** `#![forbid(unsafe_code)]` in every dcr-purse crate; the test utility `purse-boltread` uses positional reads rather than `mmap`, so the rule holds there too. Private keys, seeds, passphrases and derived keys are zeroed on drop, never formatted, and never logged. One upstream behaviour echoes caller-supplied WIF private keys in a `signrawtransaction` error string (spec 08); that is one of the fixes the third standing rule of §3 covers.
5. **Wallet code is boring code.** Explicit integer widths; Go's wrapping arithmetic reproduced with `wrapping_*` exactly where the Go relies on it (child-index counters with the `0xffffffff` sentinel, fee arithmetic) and checked arithmetic everywhere else; no floating point except at the RPC edge where the API defines amounts as floats; deterministic iteration orders.
6. **Every database write is crash-safe.** One atomic transaction per logical operation, with the same boundaries as Go's (what commits together in dcrwallet commits together here, because RPC-visible state depends on it); fault-injection tests on the store. dcr-purse never opens or writes a dcrwallet database (ADR-0013). One exception, decided by the project owner on 2026-11-19 (ADR-0014 Open point 2): during initial sync, header-and-filter batches and the rescan marker may be committed with relaxed durability, because a crash costs only fetching them again; anything with an effect a client, peer or VSP can see is durable before that effect.
7. **Pin, then track.** All parity claims name one upstream commit. The pin follows dcrwallet master until v2.2 is tagged, then release tags, as dcroxide's ADR-0013 does for dcrd. A `PARITY.md` ledger maps each dcrwallet package to its crate and status.
8. **Interoperate before you ship.** No milestone is accepted on unit tests alone: each has a simnet scenario against real Go peers (dcrd, dcrwallet, vspd); from M3 on against `dcrctl --wallet`; and at M7 the scenarios of M2 to M6 are repeated through Decrediton.
9. **Fast by design.** Performance is a goal everywhere, and SPV sync faster than dcrwallet's in particular (project owner, 2026-11-19; [ADR-0014](adr/0014-performance.md)). Speed is a design input from the first line, measured against the Go reference on the same machine and recorded in a bench ledger; nothing is optimised without a measurement that names the bottleneck. In a conflict: correctness of keys and funds, crash safety, constant-time arithmetic on secrets, byte-compatible RPC results and being served correctly by every node are never traded for speed; what would tell a peer more about which addresses or transactions are the wallet's is the owner's to decide case by case; looking like dcrwallet on the network is no longer a constraint.

## 6. Phase plan

Phases are ordered by dependency and sized S/M/L/XL including tests. Every exit criterion is testable. Each phase names the specs it implements; a phase is not started until its specs' "Open questions" sections have been triaged.

### Phase 0 — Scaffolding, oracle rig, decisions *(M)*

- Cargo workspace under dcroxide's lint, deny and toolchain policy; CI on Linux, macOS and Windows; fuzz infrastructure.
- `tools/oracle`: Go module pinned to dcrwallet `54b85b33`. First shims: **database dumper** (whole bucket tree as sorted hex; used to check `purse-boltread`), **logical exporter** (the canonical, format-independent text form of a wallet, covering everything dcrwallet persists (specs 01–05), with masking rules for clock- and randomness-derived fields; its format is fixed in ADR-0001 before Phase 1, and its Rust counterpart lives in `purse-udb`, held in `purse-export-check` until that crate exists), **operation-script runner** (a JSON script of `udb`/`wallet` calls with injected randomness and time → logical export plus results; its format is ADR-0002), **address deriver**.
- Pin the acceptance clients and peers by release: the Decrediton, `dcrctl`, vspd and dcrd versions are recorded next to the dcrwallet pin and move with it (D12). Decrediton's wallet launcher and its gRPC call inventory at that release are read and added to specs 19–21 before Phase 8; the specs note that Decrediton's source was not among the inputs of the deep dive.
- Docs skeleton: this brief, `specs/`, `PARITY.md`, `QUIRKS.md`, an ADR directory.
- Decision ADRs D1–D10 of §9 drafted (their status is recorded in §9 and [adr/README.md](adr/README.md)). `purse-boltread`'s dump equals the Go dumper's for every upstream fixture in `wallet/udb/testdata` and for generated databases of many shapes (`crates/purse-boltread/tests/oracle.rs`, `fixtures_match_go` and the synthetic cases); the funded simnet wallet the exit below names was never compared. The reader was built as the importer's foundation and has been a test utility only since 2026-11-18 (ADR-0013); accepted by the project owner, 2026-11-19 (ADR-0013 Open point 2): that last comparison is dropped. Two spikes inform the costliest decisions: a `redb` schema prototype measured on a large wallet's workload (for D2), and a minimal gRPC server answering `VersionService.Version` to an unmodified grpc-go client and to Decrediton over mutual TLS (for D5).
- **Exit:** CI green on three platforms; the Rust reader's dump of Go-written databases (all fixtures in `wallet/udb/testdata` plus a funded simnet wallet) equals the Go dumper's (written when the reader was the importer's foundation; it now checks a test utility); D1–D10 decided (D4 has since been superseded by ADR-0013). The reader part is met for the fixtures and generated databases, not for the funded simnet wallet (above).

### Phase 1 — Foundations *(M)* — specs 22, 02 (keys), 25, 24

- `purse-errors` first: it fixes the error text every later crate emits.
- `purse-seed`, `purse-hdkeychain`, `purse-dcrutil`, `purse-snacl`; the `dcroxide-dcrec`, `dcroxide-crypto` and `dcroxide-wire` additions.
- **Exit:** for at least 10⁶ random seeds plus every seed whose path contains a leading-zero key in a targeted search, account xpubs and the first addresses of both branches equal the Go oracle's; all `hdkeychain`, `pgpwordlist`, `walletseed`, `snacl` upstream vectors pass; secretbox/Argon2 blobs written by Go open in Rust and the reverse; error rendering equals Go's for a generated corpus of nested errors; measured by `purse-bench` against Go in one session (ADR-0014's Phase 1 row), no slower than Go on public derivation, address, script, HMAC, hash160 and base58, at most 1.15 times Go's time on the secret paths (master key, hardened and private child with the public key), and at least 1.5 times faster on 20,000 addresses.
- **Status (2026-11-19):** the four parity clauses of the exit are met, each held by tests in the normal suite; the full 10⁶-seed run is an ignored test, run once with its result recorded. What holds each clause, with test names and counts, and what is left uncovered: [PHASE1-EXIT.md](PHASE1-EXIT.md). Speed, first measured 2026-11-19 on a shared desktop ([bench-ledger.md](bench-ledger.md), first entry): public derivation, address, script, HMAC, hash160 and base58 encoding meet the row (Rust's time 0.55 to 0.95 of Go's), and 20,000 addresses are derived 1.8 times as fast; base58 decoding is at parity with Go, neither met nor missed (Rust/Go 0.98 to 1.02 over ten sessions, the verdict flipping with noise; about half of Rust's time is dcroxide-crypto's portable BLAKE-256 against Go's AVX assembly); the secret paths do not meet it (1.57 to 1.59 times Go's time against at most 1.15), because dcroxide-dcrec multiplies the generator without k256's precomputed tables (ADR-0014 O1, being changed in dcroxide). The speed clause is therefore not met until the dcroxide pin moves past that change and a dedicated machine confirms the row, base58 decoding included.

### Phase 2 — Store design *(M)* — spec 04 §5.1, D2 (spec 01 as reference)

- `purse-store`: the engine chosen in D2 and a schema designed for the wallet's hot paths, which the specs identify in dcrwallet's layout as costs to remove: balances recomputed by a full scan of unspent outputs on every call, range queries that walk every block record, no secondary indexes for address and account lookups.
- **Order that reaches a client is part of the schema.** Several API results and every coin selection follow bbolt's raw key order: accounts iterate in the byte order of their 4-byte little-endian number (0, 0x80000000, 256, …, 1, …), and input selection walks unspent outputs by raw transaction hash then big-endian output index, seeks to the first key ≥ a random 32-byte key, and relies on "previous of end is last" (spec 04 §5.1). The store keeps an index with dcrwallet's key bytes and those cursor semantics wherever order is observable, so that results are ordered as Go's and, given the same randomness, the same outputs are spent.
- The schema is versioned from day one with its own migration mechanism: each step is one atomic transaction, a database newer than the binary is refused, and a fixture of every released schema version is kept from the first release on.
- `purse-boltread`: the complete read path with the file lock, hardened against corrupt and hostile files, was built here as the importer's reader and is done. It is no longer Phase 2 work: since 2026-11-18 it is a test utility (ADR-0013).
- **Exit:** the store passes fault injection (a crash at any point leaves the last committed state) and a model-based property test; a cursor-conformance test runs the spec 04 §5.1 cases against `purse-store` and against bbolt through the oracle; a migration test applies a dummy version step with a crash injected at every write and ends in the old or the new version, never between; the schema ADR records the measured gains against dcrwallet on the same workload. The reader's criteria that stood here (its dump equal to Go's for every fixture and for large real-world-shaped databases at page sizes 4096 and 16384; fuzzing the page decoder yields errors, never panics or unbounded allocation) no longer gate the phase; accepted by the project owner, 2026-11-19 (ADR-0013 Open point 2): they stay in the test utility's own CI for as long as it is kept.

### Phase 3 — Wallet database logic *(XL)* — specs 02, 03, 04, 05

- Address manager behaviour over the new store: account types, counters, lock/unlock, imported keys, scripts and xpubs, watching-only. Key encryption stays dcrwallet's at the blob level (scrypt + secretbox, Argon2id + XChaCha20-Poly1305): the formats are tested against Go and nothing is gained by changing them. The reason once given, that imported keys would carry over without decryption, no longer applies (ADR-0013).
- Transaction store behaviour: mined and unmined logic, rollback, stake invalidation, balances, queries, the input source. Byte-level row quirks are not reproduced; RPC-visible consequences are (spec 04 separates the two). Specs 02, 03 and 05 describe what dcrwallet persists; the store's logic and the logical export must cover all of it, though not its layout.
- Wallet creation directly in the new format, from a new seed and from an existing one (the restore path).
- `purse-import` is not built (ADR-0013): no decoders for schema version 26, no conversion, no verification report, no import front end, no import corpus and no refusal tests.
- **Exit:** the operation-script differential passes on return values and logical export for a corpus covering every `Manager` and `Store` method; a wallet created by Rust and one created by Go from the same seed and passphrases have equal logical exports; *Proposed* (ADR-0013 Open point 6): the wallet shapes the import corpus was to cover (many accounts, imported keys and scripts, voting accounts, tickets in every state, multisig, VSP records, unmined and unpublished transactions) are built on both sides by the same operation scripts (ADR-0002), or reached by restoring the same seed on both sides against the same recorded chain history, and for each the logical exports are equal and a sweep of the `wallet`-level query methods returns equal results; the sweep is repeated through JSON-RPC at Phase 7 and gRPC at Phase 12; the portable upstream `udb` logic tests pass.

### Phase 4 — Transaction construction and signing *(L)* — spec 10, parts of 08

- The `NetworkBackend` trait with a scripted fake implementation, and the `Wallet` skeleton with its database handle and passphrase lock state — here rather than in Phase 5 because address buffers and `createtx` call both.

- **Exit:** with randomness injected identically and the stores holding the same UTXO set — *Proposed* (ADR-0013 Open point 6), replacing "the Rust side reached by importing the Go database": both sides reaching it by running the same operation script (ADR-0002), or by restoring the same seed against the same recorded chain history through the scripted backend, with their logical exports compared before the scenario runs — Go and Rust build byte-identical transactions for a scenario corpus (plain sends, change and no-change, dust edges, high-fee guard, multisig, sweeps, treasury); every produced transaction passes dcrd's and dcroxide's mempool acceptance on simnet; upstream `txauthor`/`txrules`/`txsizes` vectors pass.

### Phase 5 — Chain processing and wallet core *(L)* — specs 06, 07, 08, 09

- Sidechain forest, header and difficulty validation (EMA and ASERT via `dcroxide-standalone`), chain switch, transaction ingestion, rescan, account and address discovery, the processed-blocks marker and birthday state.

- `purse-wsrpc` (websocket client, JSON-RPC 2.0 framing), `purse-dcrd-client` (the 25 dcrd methods and 5 notifications), `purse-rpcsync`.
- **Exit — milestone M2:** *Proposed* (ADR-0013 Open point 6), replacing "imports a Go-created simnet wallet": dcr-purse restores a Go-created simnet wallet from its seed, syncs through dcrd **and** through dcroxide, tracks sends and receives, survives dcrd restarts and reorgs, and agrees on balances and history with a Go dcrwallet restored from the same seed against the same chain. Then the same on testnet3, compared account by account with Go.

### Phase 7 — JSON-RPC server *(XL)* — specs 16, 17, 18

- Transport (HTTP/1.1 POST and websocket in dcroxide's in-tree style), authentication, dispatch, passthrough to dcrd, `purse-rpctypes` descriptors over `dcroxide-dcrjson`, help data, then the 103 handlers in dependency order. The logical exports are compared before replay, so a golden difference is never a difference of state. States that cannot be produced under injection (those that need a live sync) are compared under the capture masks of spec 23 §5.8.4, or structurally as spec 23 §5.8.3 does for live results.

- **Exit — milestone M7:** golden unary and stream captures match; Decrediton at the pinned release runs unmodified against dcr-purse on all three operating systems through wallet creation, restore (the only way an existing dcrwallet wallet reaches dcr-purse under Decrediton, ADR-0013), both sync modes, sending, ticket purchase with a VSP, mixing, and voting preferences, including being launched and supervised over the pipe IPC; the scenarios of M2 to M6 are repeated through it.

### Phase 13 — Hardening, performance, release *(L, then continuous)*

- External security review focused on key handling, the storage engine, RPC authentication and the mixing client; fuzz and differential soaks promoted to scheduled runs; mutation testing on the database and transaction-construction crates.
- Performance against Go: open time (scrypt dominates), rescan and discovery throughput, SPV initial sync, RPC latency on large wallets, memory.
- Backup and recovery: a documented, tested procedure for backing up the dcr-purse database (D15), and a standing CI job that upgrades every released schema version to current.
- Release engineering under dcroxide's ADR-0014 policy.
- **Exit — 1.0:** all W1–W7 suites green at the pin; a multi-month mainnet soak of paired Go and Rust wallets on copies of the same seeds with zero divergence in logical export; review findings resolved.

## 7. Testing & verification strategy

The full design, with the inventory of every upstream test file, is [specs/23-upstream-tests-oracle-plan.md](specs/23-upstream-tests-oracle-plan.md). The layers:

**Layer 1 — Ported upstream tests.** Everything upstream has that still applies: the `udb` logic tests (not the upgrade tests, whose fixture databases at versions 1–24 are kept as inputs of the test utility `purse-boltread` and of `purse-snacl`'s tests; upstream ships no version-26 fixture), `txauthor`/`txrules`/`txsizes`, `rpc/jsonrpc/types`, `pgpwordlist`, `walletseed`, `snacl`, `errors`, and the few tests in `wallet`. The `walletdb` interface tests exercise a read-write bucket API dcr-purse does not implement and are not ported. This is necessary and nowhere near sufficient.

**Layer 2 — Oracle vectors and operation-script differentials.** The core of the plan. Go shims linked against dcrwallet at the pin, with `crypto/rand` and the clock replaced by injected sources, run the same scripted operations as the Rust code; the comparison is every return value plus a **logical export** both sides can produce (accounts, addresses and counters, credits and debits, balances, tickets, preferences in a canonical form), since the two databases share no byte format. This is what pins the transaction store, the address manager, transaction construction and wallet creation. The logical export (ADR-0001, proposed) remains the means of comparing a Go wallet with a Rust wallet; its strictest use, importing a Go-written database and comparing against Go on the original, is gone with the importer (ADR-0013). Both sides now reach the same state by running the same operations (the operation-script runner, ADR-0002, proposed) or by restoring the same seed against the same chain, and the export is compared there, in the restore differentials of Layer 6 and in the paired soaks of Layer 7. Its conformance checks (`purse-export-check`) cross-read Go-written databases with `purse-boltread`. The CI fails rather than skips when the oracle is missing, as dcroxide's does.

**Layer 3 — Golden captures of both RPC surfaces.** Requests and raw response bytes recorded from Go dcrwallet against prepared wallet states on simnet (via the dcrtest harness), for every method and every error exit the specs enumerate, replayed against dcr-purse holding the same state, reached as Phase 7 describes (*Proposed*, ADR-0013 Open point 6). Where a response contains nondeterministic content, the capture records which bytes are masked and why.

**Layer 4 — Property tests.** Every codec round-trips; `purse-store` against an in-memory model; `purse-boltread` against Go-written files of random content, while the test utility is kept; address-buffer and counter invariants; balance equals the sum over unspent credits under random histories.

**Layer 5 — Fuzzing.** Every row decoder of dcr-purse's own store, JSON-RPC request parsing, protobuf decoding, P2P message handling from a hostile peer, VSP responses, mix messages, config and INI parsing, seed and extended-key parsing; bolt page decoding on corrupt files for the test utility, while it is kept.

**Layer 6 — Restore** (replaces the Import layer, which went with the import, ADR-0013; contents *Proposed*, ADR-0013 Open point 6). Restore-from-seed differentials against Go, on simnet and on testnet3. Go builds wallets of many shapes on a chain: used accounts with gaps between them, addresses used at, inside and beyond the gap limit on both branches, legacy and SLIP0044 coin types (used and unused, so that the upgrade rule of spec 09 §4.16.1 steps 7–9 is exercised both ways, and with `disablecointypeupgrades`), tickets, mixed accounts, plus the non-seed state that must not reappear (imported keys and scripts, voting accounts, account names, preferences). Go and Rust then each restore the seed with the same options against the same chain, in RPC mode (exists-address index, spec 09 §4.16.4, §4.16.6) and in SPV mode (committed filters, §4.16.2, §4.16.5), at the default gap limits and at small and raised ones. Compared: the accounts found, by number; the last-used and last-returned index per branch; the active coin type; the birthday and rescan point; the logical export after the rescan (balances by category, mined history, tickets and commitments); the probe decisions and outcomes, which must be the same (not the requests the backend saw: ADR-0014's R1, R2 and R6–R8 change those, and under S15 "the same filters" means those above a typed birthday), with the committed-filter account probe sequence (spec 09 Q-11) matching, or differing exactly as its quirk decision says; and that funds beyond the gap limit are missed by both and found by both once the limit is raised. Standing CI job on simnet; testnet3 on a schedule.

**Layer 7 — Ecosystem acceptance on simnet and testnet3.** The matrix: backend {dcrd, dcroxide} × sync mode {RPC, SPV} × scenario {send/receive, reorg, restore from seed, ticket purchase solo and VSP, vote, agenda and tspend votes, mixing with Go peers, mixed tickets} × client {`dcrctl --wallet`, Decrediton, a gRPC golden client}. Voting scenarios run in RPC mode only: dcrwallet refuses `--spv` together with `--enablevoting` ("SPV voting is not possible"), and dcr-purse reproduces that refusal. Paired-wallet soaks (Go and Rust on copies of one seed) with logical-export comparison are the wallet's equivalent of dcroxide's per-block comparator.

**Nondeterminism** is the main obstacle to differential testing and is handled deliberately: every use of `crypto/rand` (coin selection, output shuffling, nonces, jitter, mixing PRNG seeds), every clock read stored in the database, and every map iteration that reaches an output is catalogued in the specs; the Rust code takes its randomness and time from injectable sources so that tests can align the two implementations.

**Gates.** Crates on the W1/W2 surfaces (`purse-hdkeychain`, `purse-snacl`, `purse-store`, `purse-udb`, the discovery code in `purse-chain` (accepted by the project owner, 2026-11-19, ADR-0013 Open point 1: W2 is now the restore path), `purse-txauthor`, the signing paths, `sntrup4591761`, `purse-mixclient`) require differential coverage against the Go oracle, a fuzz soak, and an adversarial review of every change, under the same single-maintainer arrangement dcroxide's §7 records. `purse-import` has left the list: it is not built (ADR-0013).

## 9. Decisions the team must surface before or during Phase 0

Each becomes an ADR. Recommendations are the brief's, not settled outcomes; the specs' "decisions needed" lists hold the many smaller ones. Where a decision has an ADR, its number and status are appended as [adr/README.md](adr/README.md) records them; the ADR holds the decision, and the entry keeps the question and recommendation as first put, which the ADRs cite.

- **D1 — Name and drop-in identity.** dcroxide runs under its own name and data directory, which means an existing `dcrd.conf` must be pointed at. A wallet has a harder version of that question because the database is the point: Decrediton launches a binary called `dcrwallet` and the user's funds are in `~/.dcrwallet`. With its own database format, sharing dcrwallet's data directory would put two different `wallet.db`-like files side by side, so the question becomes where dcr-purse keeps its data. The options and recommendation as first put also covered an import (until 2026-11-18): (a) own name, own data directory, an explicit import command; (b) the same, plus an offer to import when a dcrwallet directory exists and dcr-purse has no wallet yet; (c) also installable as `dcrwallet` for Decrediton, which then needed the import to happen without a prompt; *Recommendation:* (b), with (c) designed in Phase 8 against Decrediton's actual launch sequence; and decide what `version` and the P2P user agent report. The decision was also to fix the import front end and the files an import carried over, which ADR-0013 removed. **Status:** [ADR-0005](adr/0005-name-data-directory-and-import-front-end.md), Accepted (project owner, 2026-11-18), with the dcrd certificate fallback also trying dcroxide's directory; its import front end voided by ADR-0013 the same day. What stands: (a) without the import, the name and prefix, the own data directory, config and log names, and the version string. Still open: (c), which waits for a Phase 8 addendum; without an import, Decrediton creates or restores the wallet through its own flow (§1, item 6).
- **D2 — Storage engine and schema.** *Engine decided (project owner, 2026-11-14): `redb` is the default candidate, as in dcroxide's ADR-0004, to be confirmed by a Phase 0 prototype measured against a large wallet's workload.* Still open: the schema. The specs show where dcrwallet's layout costs time: full unspent scans for every balance, no secondary indexes for address and account lookups, history queries that walk block records. Keep the transaction boundaries of the Go code so observable ordering is unchanged; version the schema from the start. **Status:** ADR-0003, accepted: engine `redb` 5 (project owner, 2026-11-18), schema (project owner, 2026-11-19). The schema owes nothing to an importer (ADR-0013); whether it stores output scripts as offsets into the transaction decides `PkScriptLocs` (§5).
- **D3 — How dcroxide crates are consumed.** Wallet crates inside the dcroxide workspace, a sibling workspace with pinned git dependencies, or published crates. *Recommendation:* a separate workspace depending on dcroxide at a pinned revision, with the additive changes landed in dcroxide first; this needs an allow-listed git source in `deny.toml`. **Status:** [ADR-0006](adr/0006-consuming-dcroxide-crates.md), Accepted (project owner, 2026-11-18), with dcr-purse kept on the latest stable Rust.
- **D4 — Which dcrwallet databases can be imported.** [ADR-0007](adr/0007-importable-dcrwallet-databases.md): superseded by ADR-0013 (2026-11-18). History: decided 2026-11-14, schema version 26 only; refined 2026-11-18, should dcrwallet raise its database version before v2.2, that version only. The same day the import itself was dropped, so no version is importable and dcrwallet's database version is not tracked. The questions it left open (whether an import carries stored headers and committed filters; whether a seed-only restore is the documented fallback) fall away: seed restore is the only path.
- **D5 — gRPC transport and protobuf.** (A) `tonic`/`prost` on `tokio`/`hyper`/`h2`, which imports the async runtime dcroxide's ADR-0005 decided against; (C) in-tree HTTP/2, HPACK, gRPC framing and a protobuf codec, consistent with dcroxide's in-tree HTTP/1.1 and websocket; (B) something between. The proto is plain proto3 with no maps, oneofs or optional fields, so the codec is small either way; HTTP/2 is the cost. *Recommendation:* decide on the Phase 0 spike; lean to (C) with (A) confined to the gRPC listener as the fallback if the spike shows HTTP/2 flow control and keepalive parity to be out of proportion. **Status:** decided (project owner, 2026-11-19; ADR-0004): (A), `tonic` and `prost`, with the `tokio` runtime confined to the gRPC listener (ADR-0008's permitted seam) and everything behind it on threads.
- **D6 — Concurrency model.** dcroxide is OS-threaded throughout. The wallet has more blocking request/response state machines (about thirty in the P2P layer, the mixing client's timed stages, long-lived gRPC streams) and Go code that holds mutexes across network I/O and across database transactions. *Recommendation:* keep OS threads and port the Go structure closely, so that lock ordering and delivery ordering can be audited against the specs; revisit only if D5 forces a runtime in. **Status:** [ADR-0008](adr/0008-concurrency-model.md), Proposed; `crossbeam-channel` for channels and `select` accepted (project owner, 2026-11-18).
- **D7 — Version skew against dcroxide.** dcroxide tracks dcrd master; dcrwallet links tagged dcrd modules. Known deltas that matter: `addrmgr` v3.0.0 against the v4 generation dcroxide ports; the mainnet HTTPS seeder list (four hosts at dcrd master, three in `chaincfg` v3.3.0); `rpc/jsonrpc/types` v4.4.0 against master's v5; go-flags v1.5.0 against v1.6.1 and logrotate v1.0.0 against v1.1.2; and, separately from any dcrd skew, `dcroxide-mixing`'s three node-policy rules that are stricter than dcrd's own pool (a per-identity key-exchange cap, one-message-per-type applied to un-orphaned messages, the expiry latch). The P2P protocol version is a parameter (11), not a skew. *Recommendation:* per module, a recorded diff between the tag dcrwallet pins and the commit dcroxide ports; reuse where the diff is empty or irrelevant to a client, parameterise where it is not. **Status:** [ADR-0009](adr/0009-version-skew-against-dcroxide.md), Accepted (project owner, 2026-11-18); the record is `docs/SKEW.md`.
- **D8 — Mixing root solver.** Spawn the external `csppsolver` (needs a Go `net/rpc` + gob client), ship a native solver, or both. *Recommendation:* native solver, verified against the Go solver's outputs, with `--csppsolver` still accepted; timing at 64 peers must fit the stage deadline. **Status:** [ADR-0010](adr/0010-mixing-root-solver.md), Accepted (project owner, 2026-11-18).
- **D9 — Error-message fidelity.** Messages reach clients verbatim and embed operation names, kind strings and, at the leaves, text from Go's standard library. *Recommendation:* byte-exact for everything dcrwallet authored (Op names, kinds, separators, its own format strings); exact code plus best-effort text for leaves authored by Go libraries, with the list of such leaves kept in PARITY.md. **Status:** [ADR-0011](adr/0011-error-message-fidelity.md), Accepted (project owner, 2026-11-18).
- **D10 — Standing quirk policy.** As stated at the end of §3: reproduce by default; errors instead of panics; deterministic order instead of map order; fix what would lose funds or leak secrets. **Status:** [ADR-0012](adr/0012-standing-quirk-policy.md), Accepted (project owner, 2026-11-18), with QK-0279 fixed instead of reproduced. Its Rule 8 now governs only the test utility `purse-boltread` (§3).
- **D11 — Notification delivery.** Go sends on unbuffered channels while holding the notification server's mutex, sometimes inside an open database write transaction, so a slow gRPC subscriber stalls the wallet. *Recommendation:* preserve per-client ordering and the points at which notifications are generated, but decouple delivery with bounded per-client queues; record the divergence. **Status:** [ADR-0015](adr/0015-notification-delivery.md), Proposed: notifications generated at Go's points with Go's content, pushed onto a queue per client counted in bytes (8 MiB per client, 256 MiB for all notification streams together), a full queue or a full budget ending the stream of the client furthest behind with a status instead of stalling the wallet; the sync streams keep Go's back-pressure. It finds that JSON-RPC clients receive no notifications at the pin, and that a stalled stream holds about 200 KB in grpc-go before the wallet blocks (measured; QK-0737).
- **D12 — Upstream tracking.** Follow dcrwallet master until v2.2 is tagged, then release tags; the dcrwallet and dcrd pins move together. **Status:** [ADR-0016](adr/0016-upstream-tracking.md), Proposed: until v2.2.0 the pin moves to master's head at a dcrwallet point release, at an upstream fix of a tracked defect, when a phase needs it, or on the owner's word; from v2.2.0, every release tag of the newest line, master read ahead into dated notes. The dcrd modules follow dcrwallet's `go.mod` and are no separate pin; the acceptance releases are recorded beside the pin; dcroxide's revision moves under ADR-0006. Each move is one signed change from a review list built by a `tools/pinmove` command still to be written. A prototype measured 7,929 citations of dcrwallet at the pin in `docs/`: a move of 8 commits shifts 295 and touches 20, one of 50 shifts 2,123 and touches 257 (a range counts as touched when any line inside it changed or it stopped being contiguous).
- **D13 — Upstream defects worth reporting.** The deep dive found behaviours that look like real defects in dcrwallet (among them a possible nil dereference in the wallet's difficulty validation (`isAncestorOf`, reached by a header that forks below the cached anchor; whether a peer can deliver one is unconfirmed), caller-supplied WIF private keys echoed in a `signrawtransaction` error string, and outpoint locks leaked on partial VSP purchases (fee inputs for the unpublished tickets stay locked until restart)). Decide who reports them upstream and when; none has been independently confirmed by running code. **Status:** [ADR-0017](adr/0017-upstream-defects.md), Proposed: 18 security-relevant candidates, to be reported privately through the Decred bug bounty by the owner, each after a run on dcrwallet's current master and latest release, and a selected list of other defects for public issues once confirmed; nothing is reported by the record. Five were confirmed by running Go at the pin for it, among them the nil dereference (QK-0227; by reading, reachable from an SPV peer that serves the wallet's start-up header sync, not by announcement to a synced wallet) and the echoed WIF keys (QK-0201). The leaked outpoint locks (QK-0279), fixed in dcr-purse, are proposed as a public issue, since ADR-0012 names them as its example of a candidate. The repository is private; publishing it would disclose the security-relevant candidates.
- **D14 — The way back to dcrwallet.** As first put: "Import is one-way. Decide whether dcr-purse offers an export of what cannot be re-derived from the seed (imported keys, scripts, xpubs, account names, preferences) so that a user can rebuild a dcrwallet wallet, and what the user documentation promises." Its premise, a one-way import, went with ADR-0013: going back is a seed restore into dcrwallet, with the same losses as the move to dcr-purse (§1). accepted by the project owner, 2026-11-19 (ADR-0013 Open point 4): reframe D14 as moving the state the seed does not carry (§1, item 2) by hand, in either direction, answered by user documentation that names the RPCs to use, with no export command. The RPC helper that reads a running dcrwallet (§1) is a possibility the owner was told about, not a plan.
- **D15 — Backup and recovery of the own-format store.** File copy when stopped, a consistent snapshot while running if `redb` allows it, and what a user restores from. **Status:** [ADR-0018](adr/0018-backup-and-recovery.md), Proposed: the running wallet copies a read transaction's snapshot into a new store file, compacts it and publishes it by rename, through a JSON-RPC `backupwallet` limited to the data directory's `backups/`; a separate tool verifies and restores; no encryption beyond what the store seals. It finds that a fresh snapshot copy is not compact (570 MB, 412 MB after an explicit compaction), against ADR-0003 item 8, and proposes an addendum to ADR-0003. A raw copy of a running store produced unopenable files in 28 of 45 plain `cp` copies under a writer, and every copy that opened needed repair (measured on redb 5.0.0; the rate depends on the machine and load).

**Open points left by dropping the import.** They are listed once, in [ADR-0013](adr/0013-no-import-seed-restore-only.md), "Open points", each with its answer; points 1, 2, 3, 4, 5 and 7 were decided as proposed on 2026-11-19 and points 6, 8 and 9 are for the owner to accept or change; none is decided. In brief: (1) the W2 contract and R2 (§3, §10) and the gated discovery code (§7); (2) whether `purse-boltread` stays, and its former Phase 0 and Phase 2 criteria; (3) first start when a dcrwallet directory exists (Phase 8); (4) user documentation for moving non-seed state, D14 reframed; (5) keeping dcrwallet's gap-limit defaults; (6) how the tests that relied on import reach matching state (Phases 3 to 8, §7 Layers 3 and 6, M1, M2); (7) watching-only wallets; (8) further points found after the decision; (9) `PkScriptLocs` (§5).

## 10. Top risks & mitigations

- **R1 — Key-derivation divergence.** A fixed 32-byte private-key type erases the stripped/unstripped distinction and about one seed in 128 derives wrong keys somewhere on the wallet path. Mitigation: the Phase 1 exit criterion, targeted leading-zero vectors, and a restore-from-seed comparison against Go in every later milestone.
- **R2 — A restore that misses funds, or users stranded without a seed** (replaces "Lossy or wrong import", which went with the import, ADR-0013; the whole entry was accepted by the project owner, 2026-11-19, ADR-0013 Open point 1, quoted). "A restore finds fewer accounts or addresses than hold funds — through the gap limits, a discovery difference from dcrwallet (the two discovery variants of spec 09 §4.16, the account probe sequence of spec 09 Q-11), or coin-type handling (spec 09 §4.16.1 steps 7 to 9; `disablecointypeupgrades`) — and the user believes the balance complete; funds that only imported keys or scripts control are never found by discovery; and a user who has lost the seed cannot migrate at all. Mitigation: the Phase 1 key vectors and the restore differentials of §7 Layer 6, which show that dcr-purse finds what dcrwallet's restore of the same seed finds, at small, default and raised gap limits and for both coin types; and the user documentation of ADR-0013 Open point 4. The new store's own corruption risk is covered by an established engine plus fault injection."
- **R3 — Untested upstream behaviour.** Most of what must match has no upstream test, and the specs were derived by reading. Mitigation: the oracle rig precedes implementation in every phase; spec statements flagged UNVERIFIED or "derived from reading only" are settled by an oracle run before code depends on them.
- **R4 — Silent mixing incompatibility.** Any deviation makes honest peers blame the Rust wallet; the user sees only mixes that never complete. Mitigation: byte-level KEM and PRNG vectors, sessions against Go peers at every denomination, induced-failure runs.
- **R5 — The gRPC transport.** Either an async runtime enters a wallet process or the project owns HTTP/2. Mitigation: the Phase 0 spike and D5; gRPC is last in the plan so it cannot hold the JSON-RPC drop-in hostage. Decided for the runtime at the listener only (tonic, ADR-0004); what remains of the risk is tonic's speed at many calls in flight and its differences from grpc-go, both measured again when the listener exists.
- **R6 — Go-specific observable behaviour.** Float formatting, `nil` versus empty slices in JSON, Go's unstable sort order in `listunspent`, float-to-integer overflow in `NewAmount` (differs by CPU architecture), HTML escaping in JSON strings. Mitigation: dcroxide's Go-JSON emitter; golden captures; each case has a decision in specs 16–18.
- **R7 — Lost votes or unregistered tickets.** A wrong vote or a broken fee-payment sequence costs users rewards. Mitigation: vote byte-equality against Go on simnet across agenda states; VSP sequence tests against a real vspd including restarts.
- **R8 — Filter completeness.** One missed `loadtxfilter` or cfilter match-set entry and the wallet silently misses its own transactions. Mitigation: paired-wallet soaks with logical-export comparison; discovery and rescan differentials.
- **R9 — Version skew with dcroxide** (D7) and **a moving upstream** (D12).
- **R10 — Underestimation and review scarcity.** Milestones are ordered so partial completion is still useful: M1 gives the Rust ecosystem `hdkeychain`, seeds, dcrwallet's key sealing and a wallet store with dcrwallet's database logic; M3 is a usable JSON-RPC wallet.

| **M2 — Syncing wallet (RPC mode)** | P4–P6 | Go-created wallet restored from its seed, synced through dcrd and dcroxide, sends and receives, in agreement with Go restored from the same seed, and on balances and mined history with the original Go wallet, which holds only seed-derived state within the default gap limits (*Proposed*, ADR-0013 Open point 6, replacing "imported … in agreement with Go on the original") |
| **M3 — JSON-RPC drop-in** | P7–P8 | golden suite (non-deferred methods) and `dcrctl --wallet` sweep green; config and IPC parity; paired-wallet soak |
| **M4 — Staking** | P9 | tickets, VSP, votes byte-equal to Go's on simnet |
| **M5 — SPV** | P10 | mainnet and testnet3 SPV sync equal to Go's and at least 1.5 times faster (provisional, ADR-0014); no bans in mixed fleets |
| **M6 — Mixing** | P11 | mixes complete with all-Go peer sessions; blame parity |
| **M7 — gRPC and Decrediton** | P12 | Decrediton unmodified on three operating systems |
| **M8 — Hardened 1.0** | P13 | external review resolved; multi-month paired mainnet soak clean; signed release |

Sizing guidance, not a promise: P3, P7, P11 and P12 dominate. Dropping in-place database compatibility (2026-11-14) removed what had been a whole L-sized phase (a write-compatible bbolt engine) and the upgrade chain from the creation path, leaving a read-only importer in their place. Dropping the import (2026-11-18, ADR-0013) removes that importer too: the decoders for every bucket, key and value of schema 26, the conversion, the verification report, the import front end (command, first-start offer, carried configuration and TLS files), the version-26 import corpus with its refusal cases and standing CI job, and the tracking of dcrwallet's database version. P3 shrinks by that much; whether it stays XL is for the team to re-estimate. What the change adds is small: the restore differentials of §7 Layer 6, which exercise discovery and rescan code that Phases 5, 6 and 10 build anyway, and the user documentation R2 calls for. Calendar estimates should come from the team after Phase 1, when the oracle rig gives real porting-velocity data. P9 and P10 are independent of each other after M3 and can run in parallel. P11's protocol work (`sntrup4591761`, `purse-mixclient`, the solver) can start alongside them, but its wallet integration needs P9 and, for mixing in SPV mode, P10; P12's transport spike starts in Phase 0 so that its answer is known long before it is needed.

## 12. Working agreements — definition of done for every task

A task is done when: (1) the implementation matches dcrwallet at the pin, with any quirk reproduced or its divergence recorded; (2) the corresponding upstream tests, where any exist, are ported and passing; (3) the behaviour is pinned by oracle-generated vectors or a differential test, not by hand-written expectations; (4) new parsers and state machines have fuzz and property targets in CI; (5) code on the W1/W2 surfaces has been through an adversarial review and lands in a commit the project owner signs; (6) `PARITY.md`, `QUIRKS.md`, the relevant spec and any ADR are updated — a spec found wrong is fixed in the same change; (7) secrets handled by the change are zeroed and unformattable; (8) public items are documented.

The first sprint, as suggested before work began: the Phase 0 rig with the database dumper and `purse-boltread`, `purse-errors`, `purse-hdkeychain` with the leading-zero vectors, and the two spikes behind D2 and D5. It is done. The oracle rig with the database dumper (`tools/oracle/cmd/boltdump`), `purse-errors`, `purse-seed`, `purse-hdkeychain` and `purse-boltread` are committed, each with a differential against Go that CI runs on Linux (x86-64 and arm64), macOS and Windows ([PARITY.md](PARITY.md)). The two spikes were built (`spikes/store-redb` for D2; `spikes/grpc-intree` and `spikes/grpc-tonic` for D5): D2's engine is accepted (`redb` 5) and its schema is accepted too (ADR-0003); D5 is decided for tonic, with the runtime confined to the listener (ADR-0004). `purse-boltread`, built as the importer's foundation, has been a test utility only since 2026-11-18 (ADR-0013).
